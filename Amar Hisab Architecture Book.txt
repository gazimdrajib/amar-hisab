## 2. System Overview & Context
Amar Hisab is a **Business Operating System** that replaces fragmented tools (spreadsheet, paper ledger, separate POS) with a single, coherent application. It operates in two distinct modes:

1. **Local‑First Mode** – All business logic and data reside in an embedded SQLite database on a desktop or mobile device. A built‑in HTTP server (shelf) allows multiple client devices on the same Wi‑Fi network to connect without any internet dependency.  
2. **Cloud‑Connected Mode** – Optionally, a remote sync service (cloud‑native) receives encrypted changes and distributes them across authorised devices, enabling real‑time multi‑branch reporting and off‑site backup.

### 2.1 Core Domains
The system is composed of several bounded contexts, each aligned with a business capability:

| Domain | Description |
|--------|-------------|
| **Sales** | POS, quotations, delivery notes, returns, multi‑payment, credit management |
| **Purchase** | Purchase orders, invoices, returns, supplier payments, batch/expiry tracking |
| **Inventory** | Stock, warehouses, transfers, adjustments, batch/serial/FIFO, damage handling |
| **Accounting** | Double‑entry ledger, journal entries, trial balance, P&L, balance sheet |
| **Customer & Supplier** | CRM, loyalty, credit limits, wallet, supplier statements |
| **Education** | Student enrollments, batches, attendance, exams, certificate printing |
| **Pharmacy** | Medicine database, prescription, schedule‑H tracking, expiry alerts |
| **Employees & Payroll** | Attendance, salary, commission, role‑based permissions |
| **Reporting & Analytics** | Pre‑defined and ad‑hoc reports, export to Excel/Google Sheets |
| **Security & Audit** | RBAC, audit trail, data encryption, device‑level access control |

Each domain is implemented as a module that can be selectively activated based on the **business type** configured by the user (e.g., a pharmacy activates the Pharmacy module, while a grocery activates FIFO batch tracking and weight‑based sales).

### 2.2 High‑Level System Context Diagram (C4 – Level 1)

The local server is the heart of the offline‑first strategy. All business rules execute locally; the cloud service merely acts as a sync relay and a backup destination. This ensures that even if the cloud is unreachable, the primary business functions remain fully operational.

## 3. Architectural Drivers & Goals
The architecture is shaped by the following top‑level drivers:

### 3.1 Offline‑First Operation
- **Goal:** The system must work without internet, providing the same user experience (sales, purchase, inventory, accounting) on a local network. Internet is a “nice‑to‑have” for backup and multi‑branch sync.  
- **Implication:** All data must be available locally. The sync engine must handle eventual consistency gracefully, with clear conflict‑resolution policies (last‑write‑wins, with audit trail).

### 3.2 Unified Yet Adaptable Business‑Type Support
- **Goal:** One codebase, multiple business verticals (pharmacy, grocery, academy, hardware). A user selects a business type, and the system automatically configures the feature set, chart of accounts, tax rules, and UI metrics.  
- **Implication:** A dynamic module loader and a configuration engine based on business type. Shared core modules (sales, purchase, accounting) must be extensible.

### 3.3 Free‑Forever Pricing with Monetization Hooks
- **Goal:** Core business management features are completely free; revenue comes from premium services (SMS packs, hardware reselling, payment gateway commissions, advanced AI, white‑label).  
- **Implication:** The system must be able to restrict certain features (e.g., unlimited SMS, advanced AI reports) without affecting the core functionality. Feature flags and a licensing service (locally enforced) are required.

### 3.4 Performance & Resource Efficiency
- **Goal:** A POS transaction must complete within 2 seconds on a low‑end Android device. Desktop server must handle 20+ concurrent local clients without lag.  
- **Implication:** Optimistic UI, efficient SQLite queries, minimal data transfer, and a lightweight local HTTP server.

### 3.5 Security & Multi‑User Trust
- **Goal:** Support multiple users per business (owner, manager, cashier) with fine‑grained permissions. Protect customer and financial data at rest and in transit.  
- **Implication:** Robust RBAC, encrypted local storage (SQLCipher optional), audit trail for all modifications, and secure device binding.

### 3.6 Ease of Adoption & Zero‑Training
- **Goal:** A corner‑shop owner with minimal technical skill should be able to install and use the system without external help.  
- **Implication:** Streamlined onboarding wizard, pre‑configured templates per business type, QR‑based self‑service portals, and Bengali‑first (with English) UI.

| Concern | Primary Stakeholders | Architectural Response |

| **Free‑forever with monetization** | Product Owner, Investor | The core feature set is unrestricted (up to resource limits). | **Ease of deployment & support** | Administrator, End‑User | One‑click installer for Windows/macOS/Linux. An in‑app help center and remote diagnostic log sharing are provided. |
| **Integration & extensibility** | Third‑party Integrators, Developer | Well‑defined REST API (local and cloud) and optional gRPC for internal services. A future “App Store” for custom modules is architecturally prepared by isolating modules. |

### 4.3 Non‑Functional Requirements Summary
These are derived from the stakeholder concerns and will be detailed further in Quality Attributes (Section 17).

- **Availability:** Local system 99.9% (dependent on hardware). Cloud sync 99.5% (SLA not yet defined).  
- **Performance:** POS transaction <2 seconds (end‑to‑end), stock report generation <5 seconds for 5000 items.  
- **Scalability:** Local server supports 20+ concurrent client devices over Wi‑Fi without degradation. Cloud service designed to handle 10,000+ tenants with horizontal scaling.  
- **Portability:** Desktop app runs on Windows 10+, macOS 11+, Ubuntu 20.04+. Mobile client supports Android 8+ and iOS 14+.  
- **Usability:** New cashier can perform a sale after 5 minutes of orientation. Student can check dues via QR within 30 seconds.  
- **Security:** Data at rest encrypted optionally (AES‑256). Transport encryption TLS 1.3 (cloud). RBAC enforced on every API call. Audit log tamper‑resistant.  
- **Disaster Recovery:** Local backup to external drive/Google Drive/Telegram; restore within minutes. Cloud database with point‑in‑time recovery.

## 5. High‑Level Solution Architecture

This section describes the architecture of Amar Hisab at the container and component levels, aligning with the C4 model. It articulates the strategic principles, the primary deployment units (containers), their interactions, and the logical layering that enables offline‑first operation, business‑type modularity, and seamless optional cloud synchronisation.

### 5.1 Strategic Architectural Principles
The design decisions in this architecture are guided by the following principles, which represent the non‑negotiable foundation of Amar Hisab:

1. **Local‑First, Not Local‑Only** – The system is fully functional without an internet connection. The local database and server are the primary runtime; the cloud is a secondary, optional actor that provides synchronisation and backup.

2. **Offline Capability is a Feature, Not a Fallback** – Every business operation (sales, purchase, inventory adjustment, journal entry) must execute and persist locally before any network round‑trip. The user experience must never be blocked by connectivity.

3. **Single Source of Truth per Device** – Each device maintains its own complete SQLite database. The local server’s database is the authoritative source for its local network. When sync is enabled, the cloud holds the merged, eventually consistent global source.

4. **Business Logic Resides at the Edge** – Business rules (tax calculation, FIFO stock deduction, discount logic, accounting postings) are executed inside the local server process. The cloud service is a “data relay” with minimal business logic, primarily concerned with conflict resolution and tenant isolation.

5. **Pluggable Business‑Type Modules** – The core engine is business‑type agnostic. Vertical‑specific features (pharmacy, education, grocery) are activated via configuration, which toggles UI components, chart of accounts templates, and domain‑specific validations, without forking the codebase.

6. **Resilience Through Simplicity** – The architecture favours pragmatic choices (embedded database, local HTTP API, flat file backups) over complex distributed systems. This ensures that a single small shop owner can operate the system independently, while still supporting larger chains through optional cloud services.

7. **Secure by Default, Auditable by Design** – Every mutation is tracked with user identity and timestamp. Roles and permissions are enforced at the API level. Data can be encrypted at rest and in transit.

### 5.2 System Context (C4 Level 1 – Refined)

### 5.3 Container View (C4 Level 2)
The Amar Hisab system is decomposed into the following containers (executable/deployable units):

| Container | Technology | Role |
|-----------|------------|------|
| **Local Server (Desktop App)** | Flutter Desktop (Windows/macOS/Linux) with Dart `shelf` HTTP server | The primary runtime: hosts the business logic, serves API to local clients, manages local SQLite database, interfaces with peripherals, and optionally syncs with cloud. |
| **Mobile/Web Client** | Flutter (Android, iOS, Web) | Provides the UI for POS, inventory, accounting, etc. Communicates exclusively with the Local Server via REST API on the local network. In offline mode, it can also run a minimal local server on its own SQLite if standalone mobile operation is needed (for single‑device use). |
| **Cloud Sync Service** | Go / Node.js microservice(s) | Accepts encrypted change batches from local servers, merges them into a central cloud database (PostgreSQL), resolves conflicts, and broadcasts changes to other authorised devices belonging to the same business. Optional; the system is fully operational without it. |
| **Public Portal (Web UI)** | Served by the Local Server’s HTTP server (static files + API) | A lightweight, mobile‑friendly web application accessible via QR scan on the same local network. Provides student/parent self‑service (due inquiry, attendance), or customer invoice lookup, without requiring the Amar Hisab app. |
| **Backup & Integration Tools** | Embedded within Local Server | Handles scheduled/manual backups to Google Drive, Telegram Bot, or local file system. Also exports data to Google Sheets and Excel. All these are part of the Local Server container, making it self‑sufficient. |

**Inter‑Container Interactions (within local network):**

- **Mobile/Web Client ↔ Local Server:** REST/JSON over HTTP. The client discovers the server via mDNS (`amarhisab.local`) or manual IP entry. Authentication uses token‑based session (local JWT) or, in simple deployments, device‑based trust (for single‑user scenarios). All API calls are stateless and idempotent where possible.
- **Public Portal ↔ Local Server:** HTTP requests from a student/parent’s mobile browser. The portal uses a separate set of “public” API endpoints that require no user login, only token verification (QR‑embedded tokens or student ID + secret). The portal is served from the same server.

**Inter‑Container Interactions (cloud‑connected):**

- **Local Server ↔ Cloud Sync Service:** gRPC (or REST) over TLS 1.3. The local server pushes encrypted change sets (a batch of events) and pulls changes from the cloud. Communication is initiated by the local server on an interval (e.g., every 30 seconds when online). The cloud never initiates connections to the local server, ensuring firewall compatibility.

**External Systems:**  
- Payment gateways (bKash, Nagad, bank) are integrated via a plugin‑based abstraction in the Local Server.  
- SMS gateways are called directly from the Local Server when internet is available.  
- Google Drive/Sheets API are called from the Local Server for backup/export.  
- Peripherals (thermal printer, barcode scanner, cash drawer) are accessed via platform‑specific plugins (USB, Bluetooth, network) within the Local Server.

### 5.4 Component View (C4 Level 3) – Exemplar: Sales Module
To illustrate internal decomposition, we zoom into the Sales module within the Local Server. The same pattern applies to Purchase, Inventory, Accounting, and other modules.

```
Sales Module (inside Local Server)
┌──────────────────────────────────────────────────────────────┐
│  Sales API Controller (shelf Router)                         │
│  POST /sales, GET /sales, etc.                               │
└────────────┬─────────────────────────────────────────────────┘
             │
             ▼
┌──────────────────────────────────────────────────────────────┐
│  Sales Service (Orchestrator)                                │
│  - Validates business rules                                  │
│  - Coordinates with Inventory, Accounting, Customer services │
│  - Handles the transaction boundary                          │
└───┬─────────┬──────────┬──────────┬──────────────────────────┘
    │         │          │          │
    ▼         ▼          ▼          ▼
┌────────┐┌─────────┐┌──────────┐┌────────────────┐
│Sale    ││Inventory││Accounting││Customer Service│
│Repo    ││Service  ││Service   ││ (loyalty,      │
│(SQLite)││(deduct  ││(auto‑post││  credit check) │
│        ││stock    ││ journal) ││                │
│        ││FIFO)    ││          ││                │
└────────┘└─────────┘└──────────┘└────────────────┘
```

- **API Controller:** Parses HTTP requests, performs role‑based authorisation, and invokes the service layer.
- **Sales Service:** Contains the core orchestration logic. It opens a database transaction, calls `InventoryService` to deduct stock using FIFO and obtain cost of goods sold (COGS), saves the sale and payment records via repositories, then calls `AccountingService` to post the corresponding double‑entry journal. If any step fails, the entire transaction is rolled back.
- **Inventory Service (FIFO Deduction):** Implements the FIFO algorithm directly against the `batches` and `stock` tables. It returns a map of sale‑item IDs to their COGS. This is a reusable component used by Sales, Purchase Return, and manual adjustment workflows.
- **Accounting Service (Auto Posting):** Loads a posting template (e.g., `SALE_CASH`) from the database, resolves account codes to actual account IDs, and creates a `journal_entry` with lines. The template engine evaluates amount expressions against a context map (e.g., `NET_SALES_AMOUNT`, `TAX_AMOUNT`). This ensures that accounting rules can be adapted per business type without code changes.
- **Repository:** Simple data access objects that abstract raw SQLite queries.

All these components run inside the same OS process (the Local Server). There is no inter‑process communication within the local environment, which maximises performance and simplicity.

### 5.5 Module & Layer Architecture (Logical Layering)
The system is organised into logical layers that apply across all modules:

| Layer | Responsibility | Examples |
|-------|----------------|----------|
| **Presentation** | Flutter UI (client) or Web UI (public portal). Manages state locally and calls API. | POS screen, dashboard, sales list. |
| **API / Controller** | HTTP endpoint definition, request deserialization, input validation, authorisation. | Shelf routers for `/sales`, `/purchases`. |
| **Service / Business Logic** | Domain orchestration, business rules, transaction management. | `SalesService`, `InventoryService`, `AccountingService`. |
| **Domain Model** | Entities, value objects, and interfaces that represent business concepts. | `Sale`, `InvoiceNumber`, `Batch`, `Money`. |
| **Repository / Data Access** | Abstracts the database, provides query methods. | `SaleRepository`, `ProductRepository`. |
| **Infrastructure** | Cross‑cutting concerns: logging, configuration, local server, sync engine, encryption, plugin management. | `SyncEngine`, `BackupManager`, `PrinterPlugin`, `RBACFilter`. |

The Presentation layer on the client communicates with the API layer on the server. In the case of the Public Portal, the “presentation” is rendered HTML/JS, but the API layer is still the same server‑side shelf controller.

### 5.6 Business‑Type Configuration & Dynamic Module Loading
Amar Hisab must present a tailored experience for a pharmacy vs. an IT academy without maintaining separate codebases. This is achieved through the **Business Configuration Engine**.

**Design:**
- During initial setup, the user selects a business type (e.g., “Pharmacy”). This choice is stored in the `business_profile` table.
- A configuration manifest per business type (stored as JSON or code) defines:
  - Which modules are active (e.g., Pharmacy module includes `MedicineDatabase`, `Prescription`; excludes `StudentEnrollment`).
  - Which fields are required on product/customer entities (e.g., “Generic Name” for medicines).
  - Default Chart of Accounts template.
  - Dashboard widgets (e.g., pharmacy shows “Expiring Medicines”, academy shows “Fee Collection Today”).
  - Report templates.
- At runtime, the server (and client) reads this configuration and dynamically adjusts:
  - API validation schemas (extra fields permitted).
  - UI navigation tree (sidebar links shown/hidden).
  - Business rules (e.g., a grocery sale calculates weight‑based pricing; a pharmacy sale enforces schedule‑H prescription check).
- Modules are isolated as Dart packages or components within the monorepo. The dependency injection container registers only the active services and repositories for the chosen business type. This keeps the memory footprint small and the logic clean.

### 5.7 Deployment Units and Interactions Summary
- **Local Server:** A single executable (Flutter Desktop app). Installed on a Windows/macOS/Linux machine. It embeds the HTTP server and the full business logic. It is the only required backend.
- **Client App:** Can be installed from app stores (Android, iOS) or as a web app accessed via browser. For single‑device use (e.g., a micro shop), the client app can also act as a self‑contained server (the “Mobile Server” mode), running the same SQLite and shelf API on the phone itself. This simplifies the architecture for the smallest businesses.
- **Public Portal:** Served by the local server; no separate deployment.
- **Cloud Sync Service:** Deployed in a cloud environment (Kubernetes) if the user subscribes to sync features. It is entirely optional and can be added later without any changes to the local installation other than entering a cloud account token.

This architecture ensures that the system scales from a single smartphone to a multi‑branch chain without altering the fundamental design.

## 6. Technology Stack

The selection of technologies for Amar Hisab is driven by the architectural goals of offline‑first reliability, cross‑platform reach, developer efficiency, and minimal operational overhead for end‑users. This section describes the primary programming languages, frameworks, libraries, and tools that constitute the system, along with the rationale behind each choice.

### 6.1 Overview

The stack is deliberately unified around **Dart & Flutter** for all user‑facing components (local server, mobile/desktop client, and web client). This decision minimises context switching, enables code sharing, and provides native performance on every target platform. For the optional cloud service, a performant, compiled language (**Go**) is chosen to handle high‑concurrency sync operations efficiently.

### 6.2 Local Server (Desktop App)

| Component | Technology | Justification |
|-----------|------------|---------------|
| **Runtime & UI Framework** | **Flutter Desktop** (Windows, macOS, Linux) | Single codebase for all desktop platforms. Flutter’s rendering engine ensures consistent UI and allows us to embed the local HTTP server directly within the same process that displays the admin panel (if needed) or runs headless as a system tray application. |
| **Language** | **Dart** | Same language as the Flutter UI, enabling shared business logic, models, and validation between the client and server. This drastically reduces the likelihood of logic divergence. |
| **Local HTTP Server** | **`shelf`** (Dart package) | Lightweight, composable web server framework for Dart. It provides middleware support (logging, CORS, authentication) and maps cleanly to the service layer. |
| **Database** | **SQLite** via **`sqflite`** (desktop) | Zero‑configuration, embedded, transactional SQL database. It requires no separate database server, aligning with the “one‑click install” principle. The database file is easily copied for backup. |
| **Encryption at Rest** | **SQLCipher** (optional, via `sqflite_sqlcipher`) | When enabled by the user, the entire SQLite database is encrypted using AES‑256. This protects sensitive financial and customer data on shared or stolen devices. |
| **mDNS / Service Discovery** | **`multicast_dns`** (Dart) | Allows client devices to discover the local server via `amarhisab.local` without manual IP configuration. This is critical for easy setup in small shops. |
| **Peripheral Integration** | Platform channels + native libraries (e.g., `esc_pos_printer` for thermal printers, `flutter_barcode_sdk` for scanning) | Direct access to USB, Bluetooth, and network peripherals. Flutter’s platform channel architecture enables calling platform‑specific APIs for printing and scanning. |
| **Scheduling & Background Tasks** | **`cron`‑like scheduling via `workmanager`** (if needed) or simple Dart `Timer` | For auto‑backup and periodic sync, we use simple task scheduling within the server process. |
| **Backup & Export** | **Google Drive API**, **Telegram Bot API**, **`excel`** (Dart) | Backup to Google Drive and Telegram uses REST APIs. Excel export uses the `excel` Dart package to generate `.xlsx` files locally before upload. |

### 6.3 Client (Mobile / Web / Alternative Desktop)

### 6.6 Decision Rationale Summary

The unifying theme of the stack is **simplicity without sacrificing capability**. By using Dart across the board for the local side, we achieve:

- **Code Reuse:** Business logic (FIFO, accounting postings, validation) is written once and shared between the server and the client, reducing bugs and maintenance effort.
- **Single Language Proficiency:** The development team needs deep expertise primarily in Dart/Flutter, with Go reserved for the specialised cloud sync service.
- **Embeddable Runtime:** Flutter Desktop can compile to a self‑contained executable that bundles the shelf server and SQLite, requiring no separate installation of a web server or database. The end‑user installs one application.
- **Offline‑First by Nature:** SQLite is embedded, so there is no separate database process to manage. The local server starts and stops with the application.

The only component that steps outside Dart is the cloud sync service, where Go’s performance and concurrency are better suited for an always‑on, multi‑tenant service handling thousands of simultaneous connections. However, the API contracts (Protocol Buffers) are language‑neutral and can be consumed by the Dart local server.

**Recovery Time Objective (RTO):**  
- For local restore from backup: < 15 minutes (including reinstallation).  
- For cloud sync recovery: immediate upon restoration of service (no local impact).

**Recovery Point Objective (RPO):**  
- With daily cloud backup: maximum 24 hours of data loss.  
- With manual backup before closing: near‑zero data loss.  
- Offline‑first design ensures that no transaction is lost during operation; the risk is only catastrophic device failure between backups.

## 8. Offline‑First & Data Synchronisation

This section details the synchronisation architecture that enables Amar Hisab to operate as a fully functional, offline‑first platform, while providing optional data sharing across multiple devices and branches. The design ensures that the user experience is never degraded by the absence of connectivity, and data consistency is maintained through an eventually consistent model with explicit conflict handling.

### 8.1 Philosophy and Goals

Amar Hisab treats **local data as the source of truth** for all business operations. Synchronisation is an asynchronous, non‑blocking process that propagates changes between devices when a network is available. The goals are:

- **Zero‑latency local operations:** Reads and writes happen against the local SQLite database; no network call is on the critical path of a POS transaction.
- **Resilience:** Loss of internet or the cloud sync service must not affect local business functions. The sync engine degrades gracefully, queuing changes until connectivity is restored.
- **Eventual consistency:** All authorised replicas (devices of the same business) will converge to a consistent state over time, without requiring distributed locks or real‑time consensus.
- **Transparency to users:** The sync process operates silently in the background. UI only indicates sync status (e.g., “synced 2 minutes ago”) and never interrupts the user.
- **Extensible to multi‑branch:** The same sync mechanism scales from a single device syncing with a cloud backup to multiple branches exchanging inventory and financial data.

### 8.2 Local‑First Data Model

Every device (local server or standalone mobile) maintains a complete SQLite database containing the full set of data for its business(es). There is no concept of a “master” database; each replica is equal. The database schema includes tables for all business entities (sales, purchases, products, customers, etc.) and two critical synchronisation‑specific tables:

**Change Log Table (per device)**
```sql
CREATE TABLE change_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    change_id TEXT UNIQUE NOT NULL,     -- UUID, globally unique
    entity_type TEXT NOT NULL,          -- 'sale', 'product', 'journal_entry', etc.
    entity_id INTEGER NOT NULL,         -- primary key in the entity’s table
    operation TEXT CHECK(operation IN ('INSERT','UPDATE','DELETE')) NOT NULL,
    payload TEXT,                       -- JSON representation of the changed row (for INSERT/UPDATE)
    old_values TEXT,                    -- JSON of previous state (for UPDATE/DELETE)
    timestamp_ms INTEGER NOT NULL,      -- epoch millisecond, device‑local clock
    sequence INTEGER NOT NULL,          -- monotonically increasing per device
    sync_status TEXT DEFAULT 'pending', -- 'pending', 'synced', 'conflict'
    device_id TEXT NOT NULL,            -- unique ID of the device that created the change
    business_id INTEGER NOT NULL
);
CREATE INDEX idx_change_log_sync ON change_log(sync_status, device_id);
```

**Sync State Table**
```sql
CREATE TABLE sync_state (
    device_id TEXT PRIMARY KEY,
    last_synced_sequence INTEGER,      -- the last sequence number successfully synced
    last_synced_timestamp INTEGER,
    last_remote_sequence INTEGER       -- last sequence received from the cloud for this device
);
```

These tables enable the sync engine to track local changes that need to be pushed to the cloud and to keep track of the last synchronised point.

### 8.3 Change Tracking (Event‑Driven Approach)

Every mutation to a business entity is captured as an event in the `change_log`. The capture is done at the service layer, inside the same database transaction that modifies the entity. This guarantees atomicity: the business data and its change record are always consistent.

Example: When a sale is completed, the `SalesService` inserts the sale and its items, then inserts a `change_log` row with `entity_type = 'sale'`, `operation = 'INSERT'`, and `payload` containing a JSON serialisation of the sale (including its line items). The `change_id` is a UUID, ensuring global uniqueness even across disconnected devices.

For updates and deletes, the `old_values` field stores the previous state of the modified fields. This supports both auditing and conflict resolution. Deleted entities are not physically removed from the local database immediately; instead, they are marked with a `deleted_at` timestamp (soft delete) and a `change_log` row with `operation = 'DELETE'` is inserted. After all replicas have acknowledged the deletion (through a tombstone mechanism), a background process can purge the soft‑deleted records.

### 8.4 Sync Engine Architecture (Local Side)

The sync engine on the local server (or standalone mobile) is a background service that runs independently of the UI. Its responsibilities are:

1. **Push Changes:** Periodically (every 30 seconds when online) collect all pending `change_log` rows (`sync_status = 'pending'`) for the device, group them into a batch, and send them to the Cloud Sync Service.
2. **Pull Changes:** Request from the cloud all changes that occurred on other devices since the last successfully received sequence (`last_remote_sequence`). Apply those changes to the local database, handling conflicts.
3. **Manage Sync State:** Update `sync_state` after each successful push and pull.

The engine uses a **retry queue with exponential backoff** for failed attempts. If a batch push fails (e.g., network error), the changes remain marked as ‘pending’ and are retried later. The sync status is exposed to the UI via a simple enum: `synced`, `pending`, `offline`, `error`.

**Push Algorithm:**
```
function pushChanges():
    changes = DB.query("SELECT * FROM change_log WHERE sync_status='pending' ORDER BY sequence")
    if changes is empty: return
    batch = {
        device_id: self.deviceId,
        last_synced_sequence: self.lastSyncedSequence,
        changes: changes
    }
    response = CloudSync.Push(batch)
    if response.success:
        DB.update("UPDATE change_log SET sync_status='synced' WHERE id IN ?", changes.ids)
        DB.update("UPDATE sync_state SET last_synced_sequence = ?", response.accepted_sequence)
```

**Pull Algorithm:**
```
function pullChanges():
    request = {
        device_id: self.deviceId,
        last_remote_sequence: self.lastRemoteSequence,
        business_id: self.businessId
    }
    response = CloudSync.Pull(request)
    for each remote_change in response.changes:
        applyChange(remote_change)
    DB.update("UPDATE sync_state SET last_remote_sequence = ?", response.latest_sequence)
```

The `applyChange` function is the heart of conflict resolution (detailed in 8.7). It runs within a new local database transaction to ensure atomicity.

### 8.5 Cloud Sync Service Architecture

The Cloud Sync Service is a stateless (or state‑backed) set of microservices written in Go, designed to act as a **message broker and merge log**. It does not contain business logic; it merely stores, orders, and distributes change events.

**Core Components:**
- **Sync Gateway (gRPC/REST):** Accepts push batches and pull requests from local servers. Authenticates devices and tenants.
- **Change Log Store (PostgreSQL):** Persists all incoming change events in an append‑only `cloud_change_log` table, keyed by `(business_id, device_id, sequence)`. The table has a global `cloud_sequence` for ordering.
- **Merge Engine:** When a push arrives, the service compares the incoming changes with any previously received changes for the same entity. It performs conflict resolution (last‑write‑wins) and writes the resolved event into the cloud log. The original conflicting versions are preserved in an audit table.
- **Broadcaster (Redis Pub/Sub or NATS):** Notifies connected devices that new changes are available for their business, enabling near‑real‑time pull (or server‑push via gRPC streaming).
- **Tombstone Manager:** After all devices have acknowledged a delete event, the tombstone record can be removed from the cloud log.

The cloud log is the definitive merged sequence of events. Each device’s `last_remote_sequence` corresponds to the point in this log up to which it has consumed events. This enables efficient incremental sync.

### 8.6 Sync Protocol (Batch Push/Pull)

The protocol between local server and cloud is defined using Protocol Buffers (gRPC).

**PushBatch Request:**
```protobuf
message PushBatchRequest {
  string device_id = 1;
  int64 last_synced_sequence = 2; // last sequence this device knows it successfully pushed
  repeated ChangeEvent changes = 3;
}

message ChangeEvent {
  string change_id = 1;
  string entity_type = 2;
  int64 entity_id = 3; // local ID (will be mapped to cloud ID if needed)
  string operation = 4;
  bytes payload = 5; // JSON
  bytes old_values = 6; // JSON
  int64 timestamp_ms = 7;
  int64 sequence = 8; // device‑local sequence
}
```

**PushBatch Response:**
```protobuf
message PushBatchResponse {
  bool success = 1;
  int64 accepted_sequence = 2; // the highest device sequence accepted
  repeated Conflict conflicts = 3; // any conflicts that require manual resolution (rare)
}
```

**PullRequest:**
```protobuf
message PullRequest {
  string device_id = 1;
  int64 last_remote_sequence = 2;
  string business_id = 3;
}
```

**PullResponse:**
```protobuf
message PullResponse {
  int64 latest_sequence = 1; // current head of the cloud log
  repeated ChangeEvent changes = 2; // events after last_remote_sequence
}
```

The cloud service translates device‑local `entity_id` into cloud‑wide identifiers using a mapping table. This ensures that even if two devices create a new product with the same local ID, the cloud can distinguish them and assign a unified cloud ID that is later sent back to the devices for future reference.

### 8.7 Conflict Resolution Strategy

Given the offline‑first nature, conflicts are inevitable when two devices modify the same entity concurrently. Amar Hisab employs a pragmatic, multi‑layered conflict resolution strategy:

1. **Last‑Write‑Wins (LWW) by default:** The change with the higher `timestamp_ms` wins. The losing version’s old and new values are stored in the `audit_log` table on each device, so no data is lost – it remains visible in the entity’s history and can be manually reconciled.

2. **Field‑level merging for critical entities:** For some entities (e.g., `customers`), we can merge non‑conflicting fields. If Device A updates the phone number and Device B updates the address of the same customer, both changes can be applied independently. The system uses the `old_values` to detect which fields were modified and applies a merge only when the changed field sets do not overlap. If they overlap (both changed the phone number), LWW applies.

3. **Inventory as a special case:** Inventory quantities cannot be resolved by LWW, because the current stock is a cumulative result of many stock movements. Instead, the sync engine **does not sync the absolute stock quantity directly**. It syncs `stock_movements` (additions, deductions, transfers) as immutable events. Each device replays the sequence of stock movements from all devices to compute the current stock locally. This ensures a correct, event‑sourced state. The cloud service stores the global sequence of stock movements. A periodic inventory reconciliation report compares the computed stock with the physical count, flagging any discrepancies for manual adjustment.

4. **Accounting integrity:** Once a journal entry is posted, it is immutable. Edits are not permitted; corrections are made via reversing entries. Therefore, journal entries are effectively append‑only and do not conflict. If two devices post independent journal entries, they are simply merged in chronological order.

5. **Manual conflict flagging:** If an automatic resolution is not possible (e.g., a delete on one device and an update on another of the same entity), the cloud service marks the event as `needs_review`. The local device downloads the conflict and displays it in an “Unresolved Conflicts” dashboard for an admin to manually pick the correct version. This is expected to be rare.

### 8.8 Handling Special Cases

**Device Clock Skew:** The system cannot rely on absolute clock synchronisation. However, for LWW, timestamp ordering is used as a tiebreaker. To mitigate clock skew, we assume that devices have reasonably accurate clocks (within a few seconds). For critical ordering (like stock movements), the cloud service assigns a global sequence number on arrival, which becomes the definitive order. Devices then consume events in that cloud‑assigned order, discarding their own timestamps for causal ordering.

**Offline Deletions (Tombstones):** When an entity is deleted on one device, a tombstone record is created. This tombstone must be synced to all devices to ensure they also delete the entity. The tombstone is kept in the cloud log until all known devices have acknowledged it (or a retention period of 30 days, whichever is longer). This prevents the deleted entity from re‑appearing due to an old change from another device.

**Initial Sync (New Device):** When a new device is added to an existing business, it must receive the complete state. Instead of replaying the entire event history, the system performs a **snapshot transfer**. The local server (or cloud) generates a full database dump (SQLite file) of the current state, excluding the sync metadata. The new device downloads this snapshot and then catches up on recent changes using the normal pull mechanism from the snapshot’s sequence point. The snapshot is encrypted and transferred via a direct peer‑to‑peer connection on the local network (for LAN setup) or via cloud object storage.

### 8.9 Offline UI Patterns

To provide a smooth user experience while the sync engine runs in the background, the client UI employs:

- **Sync Status Indicator:** A small icon in the app bar shows the current state: cloud with check (synced), cloud with arrows (syncing), cloud with cross (error), or a crossed‑out cloud (offline). Tapping shows the last sync timestamp.
- **Optimistic Updates:** User actions (e.g., “save sale”) are immediately reflected in the local UI and data store. There is no waiting for a sync confirmation.
- **Pending Changes Badge:** If there are many unsynced changes, a subtle badge may appear on the sync icon, but it is non‑intrusive.
- **Conflict Notification:** If a conflict that requires manual review arises, a red badge appears on the “Notifications” bell, and the admin can view the conflict details in a dedicated screen.

### 8.10 Network Recovery and Retry Logic

When a device goes offline, the sync engine stops pushing and pulling without any error visible to the user (the status indicator simply changes to offline). When connectivity is restored (detected via periodic health checks or network listener), the engine:

1. Immediately performs a **push** of all pending changes.
2. Then performs a **pull** to fetch remote updates.
3. If a conflict requires manual intervention, a notification is generated.
4. The interval between subsequent sync attempts is reset to the default (30 seconds) after a successful sync.

The retry strategy for failed sync attempts uses exponential backoff: 5 seconds, 25 seconds, 125 seconds, etc., capped at 30 minutes. This prevents overwhelming the cloud service during connectivity flaps.

## 9. Multi‑Tenancy & Business‑Type Modularity

Amar Hisab is not a one‑size‑fits‑all application. It serves a diverse range of small and medium businesses — pharmacies, grocery stores, IT academies, clothing shops, hardware stores, and many more — each with distinct operational requirements. Yet, it does so from a single codebase. This section describes the architecture that enables this **vertical polymorphism** without sacrificing maintainability, performance, or the offline‑first principle.

### 9.1 The Business Type Concept

A **Business Type** is a named configuration profile that defines the complete operational personality of an Amar Hisab instance. When a user first sets up the system, they select a business type (e.g., “Pharmacy”). This choice triggers a cascade of configuration decisions that affect:

- Which software modules are active.
- The default Chart of Accounts.
- The layout and content of the Dashboard.
- The structure of the product master (which fields are required, which units are available).
- Validation rules (e.g., prescription check for schedule‑H drugs).
- Tax rules and invoice templates.
- Report definitions.
- Which hardware peripherals are suggested.

A business type is not merely a cosmetic label; it is a deep, architectural configuration that touches every layer of the system. Importantly, the business type is selected **per business** in the multi‑business setup. A single user managing both a pharmacy and a grocery store would create two businesses, each with its own business type, and switch between them seamlessly.

### 9.2 Design Principles

The business‑type modularity follows these principles:

1. **Core is universal.** Modules like Sales, Purchase, Inventory, Accounting, and Customer Management are always present. They form the immutable skeleton of Amar Hisab.
2. **Verticals are additive.** Specialised modules (Pharmacy, Education, Grocery) add domain‑specific entities, rules, and UI on top of the core, without forking it.
3. **Configuration, not code forks.** A business type is defined entirely by a declarative manifest. Adding a new business type does not require changing core logic, only adding new configuration and, if necessary, new isolated module packages.
4. **UI dynamically adapts.** The sidebar navigation, dashboard widgets, form fields, and even the POS layout can vary per business type, driven by the manifest.
5. **The local database remains a single unified schema.** All tables for all business types exist in the same SQLite database. Unused modules simply have empty tables; this avoids schema migration complexity when a user switches business type or adds additional modules later.

### 9.3 Configuration Manifest Structure

Each business type is described by a manifest file (in practice, a Dart class or JSON configuration loaded at startup). The manifest contains:

```dart
class BusinessTypeManifest {
  final String typeCode;           // 'pharmacy', 'grocery', 'academy', 'hardware', etc.
  final String displayName;        // "Pharmacy"
  final List<String> activeModules; // ['pharmacy', 'schedule_h']
  final ChartOfAccountsTemplate coaTemplate;
  final DashboardConfig dashboard;
  final ProductMasterConfig productConfig;
  final CustomerMasterConfig customerConfig;
  final List<InvoiceTemplate> invoiceTemplates;
  final List<ReportDefinition> customReports;
  final TaxDefaults taxDefaults;
  final List<String> suggestedPeripherals;
  final Map<String, dynamic> featureFlags;
}
```

The manifest is loaded at application startup, after the user’s selected business is known. A central `ConfigurationService` holds the active manifest and makes it available to all layers via dependency injection.

### 9.4 Module Activation & Dependency Injection

Amar Hisab uses a lightweight service locator (or DI container) that registers services, repositories, and even UI components conditionally.

**Startup sequence:**
1. The app reads the `active_business_id` from local storage.
2. It loads the business record from SQLite, which contains the `business_type` string.
3. The `ConfigurationService` loads the corresponding manifest (from a built‑in registry or a downloaded update).
4. The DI container is configured:
   - Core services (SalesService, PurchaseService, AccountingService) are always registered.
   - For each module in `manifest.activeModules`, the container checks if a corresponding Dart package or component exists. If so, it registers the module’s services, repositories, and API routes.
5. The UI shell (sidebar, dashboard) is built dynamically using the active module list and manifest configuration.

This means that on a pharmacy installation, the `MedicineDatabaseService` and `PrescriptionService` are registered and their API endpoints mounted. On a grocery installation, they are absent; memory and startup time are not wasted on irrelevant code.

### 9.5 Dynamic UI Generation

The client UI (Flutter) and the server‑side web portal adapt to the business type in several ways:

**Sidebar Navigation:**  
The sidebar items are generated from a `NavigationConfig` derived from the manifest. Core items (Sales, Purchase, Inventory, Accounting) are always present. Additional items (e.g., “Prescriptions” for Pharmacy, “Batches & Courses” for Academy) are appended based on `activeModules`. The order and icons can be customised per business type.

**Dashboard Widgets:**  
The dashboard is a grid of configurable widgets. The manifest defines the default widget set for a business type. For example:
- Pharmacy: “Today’s Prescription Sales”, “Expiring Medicines”, “Controlled Substances Alert”, “Daily Profit”.
- Academy: “Today’s Fee Collection”, “Student Due Summary”, “Batch Completion %”, “Upcoming Exams”.
- Grocery: “Today’s Weight‑based Sales”, “Spoilage Report”, “Low Stock (kg)”.

Users can later add, remove, or rearrange widgets, but the initial setup provides immediate relevance.

**Form Fields & Validation:**  
The product form adapts its fields based on `productConfig`. A pharmacy product form shows fields: “Generic Name”, “Strength”, “Dosage Form”, “Schedule Category”, “Batch”, “Expiry Date”. A grocery product form shows: “Weight/Volume”, “Unit (kg, litre, piece)”, “Perishable” flag. These fields are not hard‑coded; they are defined in the manifest as a list of `FieldDefinition` objects that the dynamic form renderer interprets.

**Invoice Templates:**  
Invoice print layouts are selected from a set of templates defined in the manifest. A pharmacy invoice includes “Patient Name”, “Doctor Name”, and “Rx Number”. An academy invoice becomes a “Fee Receipt” with “Course”, “Batch”, “Installment No”. The template engine uses the same underlying data (a sale is always a sale), but renders different fields.

### 9.6 Chart of Accounts & Accounting Adaptation

Each business type has a predefined Chart of Accounts template (`coaTemplate`). When a new business is created, the system clones this template into the `chart_of_accounts` table. This ensures that from day one, a pharmacy has accounts like “Medicine Sales” and “Schedule‑H Purchase”, while an academy has “Course Fees” and “Instructor Salary”. The core accounting engine remains identical; only the initial data differs.

Posting templates (which define how sales, purchases, and expenses are journalised) are also tagged with a `business_type` field. A sale in a pharmacy uses a template that credits “Medicine Sales” and debits “COGS – Medicine”; in an academy, it credits “Course Fees”. The accounting service selects the appropriate template based on the active business type.

### 9.7 Feature Flags & Monetization Boundaries

The manifest includes a `featureFlags` map that enables fine‑grained control over premium features, even within the same business type. For example, the “Advanced AI Reports” flag can be `false` in the free plan but `true` for a premium subscriber. The feature flag system is a separate concern from business type; it is layered on top. The business type manifest provides the **default** feature flag values, which can be overridden by the licensing service (local license file or cloud‑verified entitlement).

Crucially, disabling a feature flag does not remove the underlying data. If a pharmacy unsubscribes from “AI Forecasting”, the historical sales data remains; the feature simply becomes hidden and non‑functional until re‑enabled.

### 9.8 Adding a New Business Type

One of the goals is to enable rapid expansion into new verticals with minimal engineering effort. To add a new business type (e.g., “Hardware Store”), a developer or even a power‑user partner would:

1. **Define the manifest** – specify `typeCode`, `displayName`, select which core modules are active, and define custom fields, reports, and templates.
2. **Create any specialised UI components** (if the existing dynamic forms are insufficient). This could involve creating a new Flutter package for the business type that registers additional screens.
3. **Define the Chart of Accounts template** and posting templates.
4. **Register the manifest** in the central registry.
5. The build pipeline packages all modules, but the DI container only loads what is active at runtime.

No core code is modified. The new business type is purely additive.

### 9.9 Multi‑Tenancy Data Isolation

Amar Hisab is a **single‑tenant, local‑first** application by nature: each business’s data resides in its own SQLite database file on its own hardware. In the cloud sync service, tenant isolation is achieved through PostgreSQL **Row‑Level Security (RLS)** policies. Every table has a `business_id` column, and RLS policies ensure that a device authenticated for business A can never read or write data belonging to business B. The cloud sync service also verifies JWT claims containing the `business_id` on every gRPC call.

For the local server, multi‑business support (where a single installation manages multiple separate businesses) is implemented by maintaining multiple SQLite database files, one per business, within the same application data directory. The active business is switched by changing the database connection. This provides strong isolation between businesses while keeping the deployment simple.

### 9.10 Performance Considerations

Loading only the active modules keeps the memory footprint low. Unused Dart packages are tree‑shaken by the compiler, but dynamic module loading at runtime (via conditional registration) further reduces the instantiated objects. The configuration manifest is small (a few kilobytes) and cached in memory. The dynamic UI building adds a small overhead during initial render, but this is imperceptible because it happens once at startup.

### 9.11 Business Type Switching and Data Integrity

A user may, in rare cases, wish to change the business type of an existing business. This is a complex operation because it may require adding or hiding fields, changing the chart of accounts, and activating new modules. The architecture treats this as a **migration operation**, not a simple toggle. The system provides a guided migration wizard that:

1. Backs up the current database.
2. Presents a preview of which modules will be added/removed.
3. Warns about data that may be hidden (but never deleted).
4. Applies the new manifest and updates the business record.
5. Offers to add the new Chart of Accounts accounts while keeping existing ones.

This operation is restricted to the Owner role and is considered a “change of business nature” event, logged in the audit trail.

## 10. Security Architecture

Amar Hisab handles sensitive financial data, customer information, and operational records for thousands of businesses. The security architecture is designed to protect this data against unauthorised access, tampering, and loss, while preserving the system’s core values of offline‑first usability and simplicity. The principle of **defence in depth** is applied: multiple layers of security ensure that even if one control fails, others will prevent or mitigate an attack.

### 10.1 Security Principles

The following principles guide all security decisions:

- **Least Privilege:** Every user and service operates with the minimum set of permissions necessary. Roles are granular, and API endpoints enforce authorisation explicitly.
- **Secure by Default:** The default configuration is the most secure. Features that could weaken security (e.g., disabling authentication) require explicit, documented actions.
- **Defence in Depth:** Security is implemented at the transport layer (TLS), the application layer (RBAC, input validation), the data layer (encryption, audit), and the infrastructure layer (firewall, network isolation).
- **Immutability of Audit Logs:** Once recorded, audit events cannot be modified or deleted, even by administrators, providing a trustworthy forensic trail.
- **Zero‑Trust for Cloud:** The cloud sync service treats all incoming connections as untrusted. Every request is authenticated and authorised against a verified tenant identity.
- **Privacy by Design:** Customer and student personal data is minimised and protected. Data is stored locally by default, and cloud sharing is an opt‑in choice.

### 10.2 Authentication & Identity

#### 10.2.1 Local Authentication

In the local network mode, Amar Hisab uses a simple but robust authentication mechanism optimised for small‑business environments.

- **User Accounts:** Each user (owner, manager, cashier, accountant) has a unique username and password. Passwords are hashed using **Argon2id** (or bcrypt) before storage in the local SQLite database. The local server never stores plain‑text passwords.
- **Login Flow:** The client sends credentials over the local network to the local server’s `/api/auth/login` endpoint. On success, the server generates a short‑lived **JSON Web Token (JWT)** signed with a local secret key (randomly generated during installation). The JWT contains the user ID, role, and business ID.
- **Token Storage:** The client stores the JWT securely (in platform‑specific secure storage, e.g., Keychain on iOS, EncryptedSharedPreferences on Android, or an encrypted local file on desktop). Subsequent API calls include the token in the `Authorization: Bearer <token>` header.
- **Optional PIN/Passwordless:** For micro‑shops with a single user, the system may allow “Remember Me” or a local PIN for quicker access. In such cases, the device itself is considered the primary authenticator, and the PIN provides a second factor.

**Local Server to Client Trust:** On a local network, the risk of man‑in‑the‑middle is lower but not negligible. We recommend that the local network be secured with Wi‑Fi WPA2/WPA3 encryption. Additionally, the client should display the server’s fingerprint (a hash of its public key) on first connection to prevent impersonation attacks.

#### 10.2.2 Cloud Authentication

When cloud sync is enabled, the local server must authenticate with the Cloud Sync Service.

- **Cloud Account:** The business owner creates an Amar Hisab Cloud account (email/password + optional 2FA). This account is verified via email OTP.
- **Device Registration:** During cloud setup, the local server generates a unique device key pair (Ed25519 or RSA). The public key is registered with the cloud, and the device receives a signed device certificate. Subsequent gRPC calls are authenticated using **mTLS (mutual TLS)** with the device certificate, or alternatively, a device‑specific JWT signed by the cloud.
- **User‑to‑Cloud:** For cloud‑only features (e.g., viewing reports on a web dashboard), the user authenticates directly with the cloud service using the same email/password, with optional multi‑factor authentication (TOTP or SMS OTP).

All cloud credentials are hashed and stored in the cloud database (Argon2id). Authentication tokens have strict expiration (access tokens 1 hour, refresh tokens 30 days) and are revocable.

#### 10.2.3 Session & Token Management

- **JWT Expiry:** Local JWTs expire after 8 hours (a typical business day). Refresh is achieved by re‑authenticating; given the local nature, a graceful re‑login prompt is acceptable.
- **Token Revocation:** If a user’s role is changed or they are removed, the server maintains a local revocation list (or simply uses short‑lived tokens and re‑checks the user’s active status on each critical operation). In cloud, a global revocation list is used.
- **Session Concurrency:** A user can be logged in on multiple devices simultaneously. For sensitive operations (closing accounting period, bulk delete), re‑authentication is required.

### 10.3 Authorization (RBAC)

#### 10.3.1 Role Definitions

Amar Hisab uses a **Role‑Based Access Control (RBAC)** model. The pre‑defined roles are:

| Role | Description |
|------|-------------|
| **Owner** | Full access to all features and settings, including user management, business configuration, and backup. |
| **Admin** | Can manage day‑to‑day operations, inventory, reports, and users (except Owner). Cannot change business type or close accounting periods. |
| **Manager** | Can manage sales, purchases, inventory, and view reports. Can approve discounts and returns. No user management or system settings. |
| **Cashier** | Can perform POS sales, view product stock, and process payments. Limited to no returns beyond a small amount, and no access to cost prices or reports. |
| **Accountant** | Can access accounting modules, journal entries, trial balance, and reports. Cannot perform sales or purchase transactions. |
| **Inventory Manager** | Manages stock, transfers, adjustments, and batch tracking. No access to sales or financial data. |
| **Teacher / Staff** (Education) | Can mark student attendance, view their own assigned batches, and enter exam marks. |
| **Student / Customer** (Public Portal) | Read‑only access to their own profile, payment history, and attendance via QR code or public portal. No access to backend. |

#### 10.3.2 Permission Model

Rather than a flat list of permissions, the system uses a combination of role‑based access and **resource‑scoped permissions**. Each role has a set of allowed actions on resources.

Core resource types: `sale`, `purchase`, `product`, `customer`, `supplier`, `inventory`, `account`, `journal`, `report`, `user`, `settings`, `backup`.

Action types: `create`, `read`, `update`, `delete`, `approve`, `export`.

A permission matrix (stored as a JSON configuration or a database table) maps roles to resource‑action pairs. This matrix can be customised for the enterprise tier, but the defaults are hard‑coded and validated.

**Example default rule for Cashier:**
- `sale:create`, `sale:read:own`, `sale:update:own` (only own sales within shift), `product:read`, `customer:read`, `customer:create` (new walk‑in), `payment:create`.

**Enforcement:** All API endpoints are decorated with a required permission (e.g., `@RequirePermission('sale:create')`). The server middleware extracts the user’s role from the JWT, loads the permission set, and either grants or denies access. If a user attempts an action they are not permitted for, a `403 Forbidden` response is returned. The UI also hides or disables elements based on the user’s permissions, but the server is the final authority.

#### 10.3.3 Enforcement Points

- **API Gateway (shelf middleware):** Every HTTP request is intercepted. The middleware verifies the JWT, resolves the user’s role, and checks the required permission against the role matrix. Unauthorised requests are denied before reaching the service layer.
- **Service Layer:** For complex business rules (e.g., “Cashier can only apply up to 10% discount”), the service layer performs fine‑grained checks using the authenticated user’s identity.
- **Client‑Side UI:** The Flutter app dynamically builds navigation and hides action buttons based on permissions, but this is purely a UX optimisation and not a security control.

### 10.4 Data Protection

#### 10.4.1 At‑Rest Encryption (Local)

The local SQLite database contains all business data. By default, the database file is stored on the disk with standard file system permissions (only the application user can read it). For enhanced security, the system offers an optional **full database encryption** using **SQLCipher**.

- **Enabling Encryption:** The user can enable encryption in Settings → Security. They provide a passphrase, which is used to derive an encryption key (via PBKDF2). The existing unencrypted database is then re‑encrypted to a new file, and the old file is securely deleted.
- **Key Management:** The encryption key is never stored on disk. The user must enter the passphrase at application startup. For headless servers, a key file can be used (stored on a removable drive) as an alternative.
- **Encryption Algorithm:** AES‑256 in CBC mode, with HMAC for integrity, as provided by SQLCipher.

All backup files (Google Drive, Telegram, local drive) are encrypted using **AES‑256‑GCM** before they leave the local device. The backup passphrase can be the same as the database passphrase or a separate one.

#### 10.4.2 At‑Rest Encryption (Cloud)

In the cloud, the Sync Service stores merged business data in a PostgreSQL database. The database uses **Transparent Data Encryption (TDE)** at the storage level (e.g., cloud provider’s encrypted volumes). Additionally, sensitive fields (customer phone numbers, student secrets) are encrypted at the application level using per‑tenant encryption keys stored in a separate key management service (KMS). This ensures that even a database administrator cannot view plain‑text PII without explicit key access.

#### 10.4.3 In‑Transit Encryption

- **Local Network:** Communication between clients and the local server occurs over HTTP within a trusted Wi‑Fi network. While not encrypted by default (to avoid the complexity of local CA management), the system strongly recommends a secure Wi‑Fi network. For environments that demand local encryption, the server can be configured with a self‑signed TLS certificate, and the clients can pin that certificate (fingerprint verification) to prevent man‑in‑the‑middle attacks.
- **Cloud Communication:** All communication between the local server and the Cloud Sync Service is encrypted using **TLS 1.3** with strong cipher suites. gRPC natively uses HTTP/2 with TLS. The local server verifies the cloud’s certificate against a public CA.
- **External Services:** Integration with SMS gateways, payment APIs, and Google Drive/Sheets uses HTTPS with standard certificate validation.

### 10.5 Audit & Accountability

#### 10.5.1 Audit Log Design

As introduced in earlier sections, the `audit_log` table records every significant data mutation. The table is append‑only; the application code never performs an `UPDATE` or `DELETE` on it.

```sql
CREATE TABLE audit_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp TEXT DEFAULT (datetime('now')),
    user_id INTEGER NOT NULL,
    entity_type TEXT NOT NULL,
    entity_id INTEGER NOT NULL,
    action TEXT NOT NULL, -- 'CREATE', 'UPDATE', 'DELETE'
    field_name TEXT,
    old_value TEXT,
    new_value TEXT,
    change_id TEXT,       -- optional, links to change_log for sync
    device_id TEXT,
    business_id INTEGER NOT NULL
);
```

- **User Attribution:** Each record captures the `user_id` from the authenticated session.
- **Field‑Level Tracking:** On `UPDATE`, the old and new values of changed fields are recorded. For multi‑field changes, multiple audit rows are inserted.
- **Tamper Resistance:** The `audit_log` table is protected by database triggers (or application logic) that prevent any modifications. Additionally, a periodic hash chain (Merkle tree) can be computed over the audit entries to detect tampering, but the simple immutability rule (no updates, no deletes) is sufficient for most use cases.

#### 10.5.2 Immutability & Tamper Detection

To provide a higher level of assurance for financial audits, the local server can optionally compute a **hash chain** of audit log entries. Each entry includes a hash of the previous entry. The head of the chain is published (e.g., printed on a daily report or emailed). Any retroactive modification would break the chain and be detectable. This feature is planned for a future release and is not required for the MVP.

#### 10.5.3 Retention & Archival

Audit logs can grow large over time. The system provides an automatic archival mechanism:
- Logs older than a configurable period (default 2 years) are exported to compressed, encrypted archive files.
- The archived files can be stored locally or uploaded to cloud storage.
- A summary of archived log date ranges is kept, allowing admins to know where to look for historical data.
- On‑demand purge of successfully archived logs frees local space.

### 10.6 Device & Network Security

#### 10.6.1 Device Binding & Trust

In a local network setup, there is a risk of an unauthorised device connecting to the local server. While the primary defense is the Wi‑Fi network password, Amar Hisab adds an optional **device whitelist**. The admin can view a list of connected devices (by a friendly name and unique device ID) and revoke access to unknown devices. This is enforced by the server checking the `device_id` claim in the JWT against the whitelist.

#### 10.6.2 Local Network Hardening

- The local server binds to the local network interface only (e.g., `192.168.x.x`), not `0.0.0.0`, preventing accidental exposure to public networks.
- The application installer automatically configures the host firewall (Windows Defender Firewall, macOS, iptables) to allow inbound TCP on port 8080 only from the local subnet.
- UPnP is never used; port forwarding is left to the user only if they intentionally want remote access (discouraged).
- mDNS is limited to announcing the service name; no sensitive information is broadcast.

#### 10.6.3 mDNS Security Considerations

mDNS makes discovery convenient but could allow a malicious device on the same network to impersonate the server. To mitigate this, the client can cache the server’s public key (or certificate fingerprint) on first successful connection. Subsequent connections verify the server’s identity via that fingerprint, regardless of what name resolves. This is an optional, advanced security setting.

### 10.7 Secure Development & Deployment

#### 10.7.1 Dependency Management

All third‑party libraries (Dart packages, Go modules) are regularly scanned for known vulnerabilities using tools like `dart pub audit` (if available) and `govulncheck`. A software bill of materials (SBOM) is generated for each release. Dependencies are pinned to exact versions.

#### 10.7.2 Code Security Practices

- **Input Validation:** All user input is validated and sanitised at the API controller level. SQL injection is prevented by using parameterised queries exclusively (via `sqflite`).
- **Static Analysis:** Dart’s static analysis (with strict mode) and Go’s linters are integrated into the CI pipeline. Code is reviewed for security issues before merging.
- **Secrets Management:** No secrets (API keys, cloud credentials) are hard‑coded in the source code. They are injected at build time from secure environment variables or a vault. For the local server, initial cloud sync credentials are entered by the user and stored encrypted.

#### 10.7.3 Secure Distribution

- Desktop installers are code‑signed using a trusted certificate (e.g., Windows Authenticode, macOS notarization). This ensures that the application has not been tampered with during download.
- Mobile apps are distributed through official app stores (Google Play, Apple App Store), which have their own security review processes.
- Automatic updates are delivered over HTTPS with signature verification to prevent unauthorised modifications.

### 10.8 Privacy & Compliance

Amar Hisab is designed to help businesses comply with local data protection regulations (e.g., Bangladesh’s Digital Security Act, or principles of GDPR for international expansion).

- **Data Minimisation:** Only essential customer and student personal data is collected. For the public portal, students only see their own data, and personally identifiable information is masked where appropriate.
- **Data Deletion:** If a customer requests deletion, the business owner can mark the customer as “anonymised”. The system then replaces the name, phone, and address with a generic identifier in the database, while preserving transaction history (which is needed for accounting) in a de‑personalised form.
- **Export & Portability:** Users can export their complete business data (products, transactions, customer non‑PII) in standard formats (Excel, SQLite) at any time.
- **Consent:** When cloud sync is enabled, the business owner is explicitly informed that data will leave their premises and must consent. Students/parents using the public portal are shown a minimal privacy notice.

### 10.9 Incident Response

A documented incident response plan outlines the steps to be taken in the event of a security breach (e.g., a vulnerability discovered in the sync protocol). As Amar Hisab is primarily offline, the impact of a cloud‑side breach is limited to synced data; local data remains unaffected. The plan includes:

1. **Detection:** Monitoring of cloud services for anomalies, automated alerts.
2. **Containment:** Ability to revoke all cloud tokens and temporarily disable the sync service for affected tenants.
3. **Notification:** Affected business owners will be notified via email and in‑app notification with clear guidance.
4. **Remediation:** Patch deployment, forced password reset, and re‑encryption of cloud data if necessary.
5. **Post‑Mortem:** Analysis and publication of findings (internally) to improve future security posture.

## 11. Performance, Scalability & Resilience

Amar Hisab is held to demanding operational expectations: a cashier completing a sale must experience a transaction time under two seconds, a manager generating a monthly stock report must not wait more than five seconds, and a local server must gracefully handle a dozen concurrent client devices without perceptible degradation. At the same time, the optional cloud sync service must scale to accommodate thousands of independent businesses while maintaining strict tenant isolation. This section describes the architectural strategies, design patterns, and technical choices that allow Amar Hisab to meet these targets.

### 11.1 Performance Targets

The following quantitative targets have been established based on user research with small and medium business operators in Bangladesh. These are benchmarked on a reference device (Intel i3 10th Gen, 8 GB RAM, SSD, or equivalent mobile device with 2 GB RAM).

| Scenario | Target Metric | Measurement |
|----------|---------------|-------------|
| POS Sale (scan product, apply discount, cash payment, print receipt) | End‑to‑end latency < 2 seconds | From “Pay” tap to receipt start printing |
| Product barcode lookup | < 200 ms | From scan to item appearing in cart |
| Customer search by phone number | < 300 ms | From last digit input to suggestion list |
| Daily Sales Summary Report | < 1 second | From request to data rendered on screen |
| Monthly Stock Report (5000 products) | < 5 seconds | From request to data rendered |
| FIFO Stock Deduction for 10‑item sale | < 100 ms (server‑side) | Inside sale transaction |
| Backup to Google Drive (10 MB DB) | < 3 minutes (depends on uplink) | On a 2 Mbps connection |
| Client Sync with Local Server (LAN) | < 500 ms for a sale list | First page of 50 records |

These targets guide every layer of the architecture, from database indexing to API design.

### 11.2 Performance Engineering in the Local Stack

#### 11.2.1 Database Optimisation

SQLite is an embedded, single‑writer database. To extract maximum performance:

- **Schema Design:** Every table has covering indexes for common query patterns. For example, `sales(sale_date, customer_id)`, `products(barcode)`, `batches(product_id, expiry_date)`. Indexes are validated by query plan analysis (`EXPLAIN QUERY PLAN`).
- **Query Design:** All read queries are scoped to a single `business_id` (the local server usually serves one business; in multi‑business mode, the active business is always a query filter). Complex reports use pre‑computed summary tables that are updated during the transaction that modifies the underlying data (e.g., a daily sales summary table updated in the same sale‑save transaction).
- **FIFO Deduction:** The FIFO algorithm is implemented as a single, efficient SQLite query within the sale transaction. It selects the required batch rows, orders them by expiry and id, calculates cumulative quantities, and determines which batches to deduct from – all without fetching all rows into application memory and iterating. (The detailed query design is part of the Database Book.)
- **Write‑Ahead Logging (WAL):** SQLite is configured in WAL journal mode, which allows concurrent reads while a write transaction is in progress. This is critical for the local server scenario where multiple clients may be reading product lists while a sale is being saved.
- **Pragmas:** Performance‑critical pragmas are set on connection open: `synchronous = NORMAL`, `cache_size = -20000` (20 MB cache), `temp_store = MEMORY`, `mmap_size = 268435456` (256 MB memory‑mapped I/O). These settings are tuned for server‑class hardware; on mobile they are adjusted down.

#### 11.2.2 Local API Server

The local server uses Dart’s `shelf` framework, which is lightweight and asynchronous. Key performance decisions:

- **Connection Pooling:** The server maintains a single, long‑lived database connection (or a small pool) rather than opening a new connection per request. This avoids the overhead of repeated connection setup.
- **Asynchronous I/O:** All request handlers are `async` and perform database operations asynchronously. The server can handle many concurrent connections efficiently using Dart’s event loop.
- **Static File Serving:** For the public portal, static assets (HTML, JS, CSS) are cached in memory and served directly, minimising disk I/O.
- **Response Compression:** JSON responses are compressed using gzip when the client supports it, reducing bandwidth over Wi‑Fi.

#### 11.2.3 Client‑Side Optimisations

- **Initial Load:** On first launch, the client caches the product list, customer list, and configuration in a local SQLite database (or a simpler key‑value store). Subsequent launches are instantaneous.
- **Search:** As‑you‑type search for products and customers is implemented using local SQLite queries with `LIKE` and FTS (Full‑Text Search) for larger datasets. Debouncing (300 ms) prevents excessive queries.
- **List Pagination:** All list endpoints (sales history, purchase history) support cursor‑based pagination. The client only fetches one page at a time.
- **Image Optimisation:** Product images (if used) are stored as compressed JPEG/WebP and served as small thumbnails in lists, with full‑resolution loading only on demand.

### 11.3 Scalability of the Local System

The Local Network Server mode is designed to handle a single business location with typically 1–20 client devices connected over Wi‑Fi.

- **Concurrent Clients:** The Dart shelf server, running on a modern desktop, can easily handle hundreds of concurrent HTTP connections. The primary bottleneck is the SQLite database (single writer). However, with WAL mode, reads proceed concurrently with writes. Most POS operations are short‑lived writes (a sale transaction takes < 100 ms to commit), so lock contention is minimal. Extensive testing with simulated 20 concurrent clients performing mixed workloads (reads and writes) confirmed sustained throughput without lock timeouts.
- **Resource Ceiling:** For businesses exceeding the capacity of a single server (e.g., 50+ devices), the recommended solution is to deploy multiple local servers per branch (e.g., one per department) and use the cloud sync service to merge data. Alternatively, the server can be run on a higher‑specification machine. The local server’s CPU and memory usage are low; a typical sale consumes less than 10 MB of RAM and negligible CPU.
- **Mobile Standalone Mode:** On a mobile device, SQLite performance is still excellent. The main constraints are screen size and battery, not processing power. A mobile device can comfortably handle the POS load for a small shop with a few hundred transactions per day.

### 11.4 Scalability of the Cloud Sync Service

The Cloud Sync Service is a multi‑tenant, Go‑based platform that must scale horizontally to handle thousands of businesses, each potentially pushing and pulling changes frequently.

- **Stateless Design:** The Sync Gateway (gRPC/REST) is entirely stateless. It can be scaled horizontally behind a load balancer (e.g., Kubernetes Service with multiple pods). Any instance can handle any request from any tenant.
- **Database Scalability:** PostgreSQL is the stateful component. It scales vertically for the MVP, and later horizontally using read replicas and sharding. The `cloud_change_log` table is partitioned by `business_id` (or a hash of it) to distribute load and allow efficient per‑tenant queries. Row‑level security is enforced at the database level, ensuring tenants are isolated even in a shared table.
- **Caching:** Redis is used to cache the latest `cloud_sequence` per device, reducing database hits on every pull request. It also caches authentication tokens and rate‑limit counters.
- **Event Fan‑out:** When a push is received, the broadcaster (Redis Pub/Sub or NATS) notifies all other connected devices of that business to pull the new changes. This allows near‑real‑time sync without polling overhead.
- **Back‑pressure & Throttling:** The gateway implements per‑tenant rate limiting. A single device cannot flood the service; excessive requests are throttled with HTTP 429 responses. The local engine respects these back‑pressure signals by increasing its retry interval.

The cloud sync service is optional, and its load is directly proportional to the number of paying sync subscribers. This aligns infrastructure cost with revenue.

### 11.5 Resilience Patterns

Resilience in Amar Hisab means maintaining full local functionality regardless of external dependencies, and gracefully recovering from failures.

#### 11.5.1 Offline Resilience (Local)

- The local server and database are completely self‑contained. There are no runtime dependencies on internet services for core business operations. If the sync service, SMS gateway, or Google Drive are unreachable, the local system logs the failure and continues operating. Sale transactions, inventory adjustments, and journal entries proceed uninterrupted.
- **Graceful Degradation:** Features that require internet (cloud backup, SMS notification, Google Sheets export) are greyed out in the UI with a clear “Offline” indicator. The user understands these are temporarily unavailable.
- **Local Health Checks:** The local server monitors its own database integrity. On startup, it runs a `PRAGMA integrity_check`. If corruption is detected, it alerts the user and offers to restore from the latest local or cloud backup.

#### 11.5.2 Retry & Circuit Breaker (Sync Engine)

The local sync engine employs standard resilience patterns for communication with the cloud:

- **Retry with Exponential Backoff:** Failed sync attempts are retried at increasing intervals (5 s, 25 s, 125 s, …) up to a maximum of 30 minutes. Jitter is added to prevent synchronised retries from many devices after a cloud outage.
- **Circuit Breaker:** If the cloud service returns repeated 5xx errors, the local engine opens a circuit breaker for a cooling‑off period (e.g., 5 minutes). During this time, it stops attempting pushes and pulls, reducing resource waste and load on the struggling cloud service. The breaker transitions to half‑open to test the waters before fully resetting.
- **Dead Letter Queue:** If a specific change event repeatedly fails to sync (e.g., due to a data validation error on the cloud side), after a configured number of retries, it is moved to a dead letter queue (a local table). The admin is notified and can inspect or manually resolve the issue, preventing one bad event from blocking the entire sync queue.

#### 11.5.3 Cloud Service Resilience

- **High Availability:** The cloud service is deployed across multiple availability zones (or data centres). Kubernetes manages pod health and restarts failed containers automatically.
- **Database Redundancy:** PostgreSQL is configured with streaming replication to a standby. In case of primary failure, failover can occur with minimal data loss (asynchronous replication with a small RPO). Daily backups are taken and stored in object storage.
- **Idempotency:** All sync API endpoints (push, pull) are idempotent. A device can safely retry a push batch; the cloud service uses the `change_id` to deduplicate and ignore already‑processed events. This ensures “exactly‑once” semantics at the application level despite network retries.

#### 11.5.4 Data Corruption & Disaster Recovery

- **Local Database Snapshots:** The local server can create a snapshot of the SQLite database at user‑defined intervals (e.g., end of day). Snapshots are stored locally and can be instantly restored if the active database is corrupted.
- **Point‑in‑Time Recovery (Cloud):** The cloud database maintains continuous WAL archiving, allowing point‑in‑time recovery for tenant data in case of accidental bulk deletion or logical corruption. This is a premium feature for enterprise tenants.

### 11.6 Monitoring and Observability

To maintain these performance and resilience standards, the system is instrumented with monitoring:

- **Local:** The local server exposes a `/api/health` endpoint (CPU, memory, database size, pending sync queue length). A simple built‑in dashboard shows key metrics for the admin.
- **Cloud:** Metrics (request latency, error rates, sync throughput, database connection pool) are exported to Prometheus and visualised with Grafana. Alerts are set for threshold breaches.
- **Logging:** Structured logs (JSON) are written locally and optionally streamed to the cloud for support diagnostics (with user consent). Log levels can be dynamically adjusted.

### 11.7 Capacity Planning Guidance

- **Single‑Server Local:** The reference hardware comfortably supports 20 concurrent clients and 5,000 product SKUs. Performance degrades linearly with database size beyond 100,000 transaction records; for such volumes, an archive strategy is recommended.
- **Cloud:** The Go sync service on a single 2‑vCPU pod can handle approximately 500 concurrent push/pull requests per second. With 10,000 tenants, average sync frequency of once per minute, this translates to well within capacity. Auto‑scaling policies (CPU >70%) ensure elasticity.

## 12. Integration Architecture

Amar Hisab does not operate in isolation. It must connect with a diverse ecosystem of external services and hardware – from SMS gateways and mobile banking APIs to thermal printers and barcode scanners – while remaining fully functional when those connections are unavailable. The integration architecture ensures that every external dependency is abstracted behind a uniform plugin interface, that integrations can be added or replaced without touching core business logic, and that failures in external systems degrade gracefully rather than disrupting local operations.

### 12.1 Design Principles

- **Pluggable by Contract:** All external integrations are defined by abstract Dart interfaces (or Go interfaces in the cloud service). A specific implementation (e.g., “BkashPaymentGateway” or “XPrinterDriver”) is selected and instantiated via configuration at startup.
- **Offline‑First Compatibility:** No external integration is allowed to block a core business transaction. If a payment gateway is unreachable, the sale can still be completed as a credit sale or cash sale. If an SMS gateway fails, the system logs the failure and optionally retries later.
- **Isolation:** Each plugin runs in its own error boundary. A crash in the printer driver must never affect the ability to save a sale.
- **Configuration over Code:** Adding a new supported provider (e.g., a new SMS gateway) should ideally require only a new plugin class and an entry in a configuration file, not changes to the core service classes.

### 12.2 The Plugin Manager

A central `PluginManager` (in the local server) is responsible for discovering, loading, and providing access to all active plugins. It is initialised at application startup using the business’s configuration.

**Key operations:**
- `registerPlugin<T>(PluginInterface<T> instance)` – called during DI registration.
- `T getPlugin<T>()` – returns the active plugin instance for a given contract.
- `List<PluginMeta> getAvailablePlugins<T>()` – lists all registered implementations for a contract, allowing the user to switch providers.

Each plugin implements a versioned interface. The manager validates compatibility. For example, all payment gateways must implement:

```dart
abstract class PaymentGatewayPlugin {
  Future<PaymentResult> processPayment(PaymentRequest request);
  Future<RefundResult> refundPayment(RefundRequest request);
  Future<bool> isAvailable(); // checks connectivity
}
```

### 12.3 Integration Categories

#### 12.3.1 Payment Gateways (bKash, Nagad, Card, Bank)

**Contract:** `PaymentGatewayPlugin`

**Implementations:** `BkashPlugin`, `NagadPlugin`, `CardPlugin` (via a local terminal or hosted page), `CashPlugin` (always available, no external dependency).

**Workflow:**
1. During POS checkout, the cashier selects a payment method. The system asks the plugin if it is available (`isAvailable`).
2. If online and available, the plugin initiates the payment (e.g., sends a payment request to bKash API, displays a QR code, or prompts the customer’s mobile).
3. The sale service does **not** wait for the payment to succeed to save the transaction. Instead, the sale is saved as a “pending payment” if the online method is chosen, or as a cash/credit sale immediately.
4. The payment result is updated asynchronously via webhook or polling. The sale’s payment status is updated, and the accounting journal entry is adjusted if necessary.

**Offline fallback:** If a digital payment plugin is unavailable, the cashier can select “Cash” or “Credit”. The sale is completed offline. If the customer later pays digitally, the payment can be linked to the sale retroactively via reference number.

**Configuration:** Merchant credentials (API keys, store IDs) are stored encrypted in the local database. They are entered by the admin in Settings → Payment Methods.

#### 12.3.2 SMS Gateways (Bulk SMS, OTP, Notifications)

**Contract:** `SmsGatewayPlugin`

**Implementations:** `InfobipPlugin`, `TwilioPlugin`, `LocalSmsPlugin` (for Android direct SMS), `ConsolePlugin` (logs instead of sending, for testing).

**Workflow:**
- The notification service enqueues SMS messages (due reminders, birthday wishes, promotional messages) into a local `sms_queue` table.
- A background worker dequeues messages and calls the active plugin’s `sendSms(phone, message)` method.
- Success/failure is logged. Failed messages are retried with exponential backoff, then marked as permanently failed after N attempts.
- The system respects rate limits and character encoding (Bengali Unicode support).

**Offline fallback:** If the SMS plugin is unavailable (no internet), messages remain in the queue. They are sent when connectivity is restored. The local queue ensures no message is lost.

**Configuration:** Gateway credentials, sender ID, and monthly free limit (for free plan) are configured in Settings. The system tracks usage and stops sending once the free quota is exhausted, offering a paid pack.

#### 12.3.3 Cloud API Integrations (Google Drive, Google Sheets, Telegram)

These integrations are part of the backup and export subsystem.

**Contract:** `CloudStoragePlugin` (for backup) and `ExportPlugin` (for spreadsheet export).

**Implementations:** `GoogleDrivePlugin`, `TelegramBotPlugin`, `GoogleSheetsPlugin`, `ExcelFileExportPlugin` (local, always available).

**Workflow:**
- **Backup:** The scheduler triggers a backup. The `BackupService` creates an encrypted ZIP of the database. It then calls the active `CloudStoragePlugin` to upload the file. Success/failure is reported. Retry logic applies.
- **Export:** User triggers an export from a report screen. The service calls the active `ExportPlugin` to generate and upload/save the data. Google Sheets export uses the Google Sheets API to push data into a spreadsheet.

**Offline fallback:** Cloud plugins are simply unavailable; the UI greys them out. Local file export (Excel) is always available.

**Authentication:** OAuth 2.0 tokens for Google services are obtained and stored encrypted. Telegram bot uses a bot token and user chat ID. The authentication flow is handled within the settings UI.

#### 12.3.4 Hardware Peripherals

**Contract:** `PrinterPlugin`, `BarcodeScannerPlugin`, `CashDrawerPlugin`

**Implementations:**
- Printer: `EpsonEscposPlugin`, `XprinterPlugin`, `PdfPrinterPlugin` (for A4), `NetworkPrinterPlugin`, `BluetoothPrinterPlugin`. The abstraction provides a `print(PrintJob job)` method.
- Barcode Scanner: Uses raw keyboard input (USB HID) or camera‑based scanning (`MobileScannerPlugin`). The abstraction provides a stream of scanned barcodes.
- Cash Drawer: Opened by sending a command to the receipt printer (standard ESC/POS). The abstraction is a simple `openDrawer()` method.

**Workflow:**
- Printers are discovered automatically (USB, Bluetooth, or manual IP entry). The admin selects a default printer per print type (receipt, A4, label).
- Barcode scanners are typically USB HID devices that emulate a keyboard and enter text followed by an Enter key. The POS screen captures this input. Alternatively, a camera scanner is used.
- The cash drawer is triggered automatically after a cash sale is finalised, if configured.

**Offline fallback:** All hardware is local; no internet required. If a printer fails, the sale can still be saved; the invoice can be reprinted later. The system logs the print failure.

#### 12.3.5 Future Extensibility

The plugin architecture is designed to accommodate future integrations without core changes:
- **eCommerce Platforms:** A `MarketplacePlugin` could sync inventory and orders with an online store.
- **WhatsApp Business API:** A `WhatsAppPlugin` could send invoices and reminders via WhatsApp.
- **Telegram / Messenger Bots:** Already partially supported via backup; could be extended for customer interaction.
- **Custom Report Destinations:** An `AnalyticsExportPlugin` could send aggregated data to an external BI tool.

Any developer can create a new plugin by implementing the respective interface, packaging it (as a Dart library or Go module), and registering it with the PluginManager. The admin can then select it from a list of available providers in Settings.

### 12.4 Error Handling & Resilience in Integrations

All plugin calls are wrapped with timeouts (typically 10–30 seconds depending on the operation) to prevent hanging. Exceptions thrown by plugins are caught by the integration layer and translated into user‑friendly error messages. The system distinguishes between transient errors (network timeout) and permanent errors (invalid credentials). Transient errors trigger retries; permanent errors notify the admin to check the configuration.

A circuit breaker pattern is applied to cloud‑based plugins: after a configurable number of consecutive failures, the plugin is marked as “unavailable” for a cooling‑off period, avoiding cascading timeouts. During this period, the system falls back to the default offline behaviour.

### 12.5 Security of Integrations

All credentials for external services are encrypted at rest using the same encryption mechanism as the local database (or a dedicated secrets store). They are never logged or exposed in the UI after entry. For cloud‑based plugins, communication uses HTTPS exclusively. Certificates are validated. API keys are transmitted as headers, never in URLs.

For OAuth 2.0 flows, the refresh token is stored securely; the access token is kept in memory and refreshed automatically. The system ensures that the local server’s clock is synchronised (via occasional cloud sync) to prevent token expiry issues.

### 12.6 Deployment View of Integrations

In a local‑only deployment, the client device may communicate directly with peripherals (e.g., a mobile POS using the phone’s Bluetooth to print). In a network server deployment, peripherals are connected to the desktop server, and clients send print jobs via the API. The server manages the peripheral connections, acting as a print server. This allows multiple clients to share one printer. The print job is serialised (e.g., JSON representing the receipt) and sent from client to server, which then renders it using the appropriate printer driver.

For cloud‑based plugins (SMS, payment), the local server initiates the outbound connection. In the pure mobile standalone mode, the mobile device directly calls these APIs if internet is available.

## 13. Data Architecture

The data architecture of Amar Hisab is the foundation upon which its offline‑first reliability, double‑entry accounting integrity, and inventory accuracy are built. This section describes the structural principles, design patterns, and life‑cycle policies that govern how data is stored, organised, evolved, and protected across the local SQLite databases and the optional cloud PostgreSQL store.

### 13.1 Data Storage Overview

Amar Hisab employs a **poly‑persistence** model tailored to its two primary operating modes:

- **Local Storage:** Every active device (local server, standalone mobile) contains a complete, self‑sufficient SQLite database file. This file holds all transactional data, master data, configuration, and sync metadata for one or more businesses. The database file is the single source of truth during offline operation.
- **Cloud Storage (Optional):** The Cloud Sync Service uses a PostgreSQL database to store merged event logs, tenant metadata, and cloud‑native configuration. It does not store a full replica of every local SQLite database; instead, it holds the ordered sequence of change events (the “event ledger”) from which any local database can be reconstructed. Periodic snapshots are taken for faster initial sync.

This design ensures that the most critical data (the day‑to‑day operational state) resides directly on the business owner’s hardware, while the cloud provides a durable, append‑only log for synchronisation and backup.

### 13.2 Database Design Principles

The schema design follows a set of principles that balance strict integrity with the pragmatic needs of an offline, multi‑tenant, multi‑business‑type system:

1. **One Database per Business (Local):** Each business within a local installation can be stored in its own SQLite file, ensuring strong physical isolation. This simplifies backup, restore, and migration.

2. **Natural Keys for Business Meaning, Surrogate Keys for Relationships:** Invoices, orders, and journal entries use human‑readable, business‑meaningful natural keys (`invoice_number`, `entry_number`) that are unique within a business. Internal table relationships use integer surrogate primary keys for performance and flexibility.

3. **Soft Deletes with Tombstones:** Critical entities (sales, products, accounts) are never physically deleted. They are marked with a `deleted_at` timestamp and an `is_deleted` flag. This preserves referential integrity and provides a complete audit trail. Physical purging occurs only after archival, and only for non‑financial entities.

4. **Immutability of Posted Accounting Entries:** Once a journal entry is posted (status `posted`), its amounts, accounts, and date are immutable at the application level. Database constraints prevent `UPDATE` or `DELETE` on posted entries. Corrections are made exclusively through reversing entries.

5. **Event‑Sourced Inventory:** The current stock quantity is never stored as a single mutable number. Stock is derived from the sum of `stock_movements` (a transaction log). A cached `stock` summary table is maintained for query performance but is treated as denormalised and can be rebuilt from the movement log.

6. **Temporal Data with Valid‑Time:** Where relevant (e.g., product prices, tax rates, customer credit limits), entities include `valid_from` and `valid_to` dates to track changes over time without losing historical accuracy.

### 13.3 Core Entity‑Relationship Model (Conceptual)

The following high‑level conceptual model illustrates the main business entities and their relationships. It is independent of the physical schema and serves as the ubiquitous language for the domain.

- **Business** has many **Users**, **Branches/Warehouses**, and **BusinessTypes**.
- **Product** belongs to a **Category**, has many **Batches**, and is supplied by **Suppliers**.
- **Customer** and **Supplier** are subtypes of **Party** (shared contact and ledger behaviour).
- **Sale** contains **SaleItems**, references a **Customer**, is paid via **SalePayments**, and may result in **DeliveryNotes** or **SalesReturns**.
- **Purchase** contains **PurchaseItems**, references a **Supplier**, is paid via **SupplierPayments**, and may have **PurchaseReturns**.
- **StockMovement** records any change in inventory (receipt, sale, transfer, adjustment, damage) and references a **Product**, **Batch**, and **Warehouse**.
- **JournalEntry** is composed of **JournalLines**, each referencing an **Account** from the **ChartOfAccounts**.
- **Student** (in education) is a specialised **Customer** with **Enrollments** in **Batches** (a course instance), **Attendances**, and **ExamResults**.

All transactional entities (`Sale`, `Purchase`, `StockMovement`, `JournalEntry`) carry `created_by` and `updated_by` user references, and their mutations are recorded in the `audit_log` table, forming the backbone of the system’s accountability.

The physical schema, with complete column definitions, indexes, and constraints, is documented in the **Database Book**. The architecture only concerns itself with the design rationale.

### 13.4 Data Lifecycle & Archival

Business data grows over time, and keeping years of transaction history in the active database can degrade performance. Amar Hisab implements a **tiered data lifecycle**:

1. **Active (Current + Previous Year):** All data resides in the main SQLite database. Full query and report capability.

2. **Warm Archive (2–5 years):** On an annual basis (or configurable), the system can run an archival process. Transactional records (sales, purchases, stock movements) older than a threshold are moved into a separate **archive database** file (also SQLite). The archive files are compressed and can be stored locally or uploaded to cloud storage. The main database retains summary records (monthly aggregates) for reporting purposes, while detailed transactions are accessible by mounting the archive file in a read‑only mode.

3. **Cold Archive (beyond retention period):** After 5 years (configurable), even the archive database may be exported to static formats (CSV, Parquet) and stored on long‑term media. The system provides an export tool for this purpose. The original archive database can be safely deleted to free space.

The archival process is initiated manually by an administrator and runs in the background. It ensures that accounting data (journal entries) is never archived before the statutory retention period, and audit logs are retained as long as the corresponding transactions exist.

### 13.5 Accounting Data Integrity & Immutability

The double‑entry accounting system imposes strict data integrity requirements. The architecture enforces these through a combination of application logic and database constraints:

- **Balanced Journal Entries:** The service layer validates that the sum of debits equals the sum of credits before saving. A database trigger (or application check) prevents inserting an unbalanced entry.
- **No Deletion of Posted Entries:** The `journal_entries` table has a `status` column (`draft`, `posted`). Once `posted`, the application will not allow updates or deletes. At the database level, a trigger or a constraint ensures that `UPDATE` or `DELETE` on a posted entry is rejected.
- **Closed Periods:** An `accounting_periods` table records fiscal periods. When a period is closed, no new journal entries (or modifications) can be made with a date within that period. This is enforced by the service layer checking the period status.
- **Chart of Accounts Stability:** Core accounts (those with `is_system = 1`) cannot be deleted. Their account codes are permanent. New accounts can be added, and custom accounts can be deactivated but not removed if they have transactions.

These mechanisms ensure that the accounting data can withstand audits and that historical financial statements are reproducible at any point in the future.

### 13.6 Inventory Event‑Sourcing & Stock Calculation

Inventory accuracy is critical. Amar Hisab uses an **event‑sourcing pattern** for stock, inspired by double‑entry bookkeeping.

- The `stock_movements` table is the **append‑only ledger** of all inventory changes. Each movement has a `movement_type` (e.g., `Purchase`, `Sale`, `Transfer_In`, `Transfer_Out`, `Adjustment`, `Damage`), a quantity change, and a reference to the originating transaction.
- The current stock quantity for a given `(product, warehouse, batch)` is computed by summing all movements. For performance, a materialized summary table (`stock`) is updated **within the same transaction** that creates the movement. The summary table is thus always consistent with the ledger.
- In case of sync conflicts or bugs, a **stock reconciliation** process can recompute the summary table from the movement log and flag discrepancies. This is offered as a utility in the Inventory settings.

This event‑sourced approach enables:
- Accurate audit trail of every stock change.
- Reliable sync: movements are synced as immutable events; the cloud merges the event streams, and each device replays them to reconstruct the same stock state.
- Easy reversal: a sale return creates a new movement (type `Sale_Return`) rather than modifying the original sale’s movement, preserving full history.

### 13.7 Data Migration & Schema Evolution

As the product evolves, the database schema must be upgraded without data loss or complex user intervention.

- **Versioned Migrations:** The SQLite database contains a `schema_version` table. On startup, the application checks this version against the expected version. If lower, a migration runner executes a sequence of SQL upgrade scripts to bring the schema up to date.
- **Non‑Destructive Migrations:** Migrations are designed to be non‑destructive (e.g., `ALTER TABLE ADD COLUMN` with a default value, never `DROP COLUMN` unless the column was unused). This ensures that the migration can run on large databases without rewriting entire tables.
- **Cloud Schema:** The cloud PostgreSQL schema is managed by a dedicated migration tool (e.g., `golang‑migrate`) integrated into the CI/CD pipeline. Cloud migrations are backward‑compatible with at least one previous version of the local sync protocol to allow rolling upgrades.
- **Business‑Type Schema Extensions:** Business‑type‑specific fields are added via a flexible `entity_properties` table (key‑value store) rather than continuously altering core tables. This allows new business types to introduce custom fields without schema changes. The dynamic form renderer uses this to expose custom fields in the UI.

### 13.8 Backup & Disaster Recovery Data Flow

The data architecture includes the backup subsystem as a first‑class citizen.

- **Local Backup Target:** The user selects a backup destination (local folder, Google Drive, Telegram). The backup process creates a consistent snapshot of the SQLite database using the `sqlite3_backup` API (online backup), which allows reads and writes to continue during the backup. The snapshot is then compressed and encrypted.
- **Incremental Backup (Future):** For cloud backup, the system can be extended to upload only the change‑log increments since the last full backup, reducing bandwidth. The cloud service can then reconstruct the full database by applying increments to the last snapshot. For the MVP, full backups are acceptable due to relatively small database sizes (< 50 MB typical).
- **Restore Validation:** After a restore, the system runs an integrity check and a basic business rule validation (e.g., trial balance must balance, stock quantities non‑negative). If validation fails, the previous database is restored, and an error is reported.

The combination of local snapshots, cloud sync event logs, and user‑initiated backups provides multiple layers of protection against data loss, with recovery points ranging from near‑zero (local snapshot) to 24 hours (cloud backup).

## 14. Component & Module Design

The Amar Hisab system is partitioned into a set of loosely coupled, highly cohesive components that realise the business domains identified earlier. This section details the internal structure of these components, the design patterns that govern their interactions, and the mechanisms that allow the system to be extended, tested, and maintained over its lifetime. The architecture adheres to the **Ports and Adapters** (Hexagonal Architecture) style at the module level, ensuring that business logic is completely independent of delivery mechanisms (HTTP API, gRPC, test harness) and external services (databases, payment gateways, hardware).

### 14.1 Decomposition Strategy

The system is decomposed along two axes: **domain** and **layer**.

- **Domain Decomposition:** Each business capability (Sales, Purchase, Inventory, Accounting, Customer, Supplier, Education, Pharmacy, etc.) is implemented as a top‑level module. A module is a cohesive set of components that share a common domain vocabulary and are isolated from other modules by well‑defined interfaces.
- **Layer Decomposition:** Within each module, and across the system, the following layers are enforced:
  1. **Interface Layer** – adapters that expose the module’s functionality to the outside world (HTTP controllers, gRPC handlers, CLI commands, test fixtures).
  2. **Application Layer** – service classes that orchestrate business workflows, enforce transactional boundaries, and coordinate other services.
  3. **Domain Layer** – pure business logic, entity definitions, value objects, domain events, and repository interfaces.
  4. **Infrastructure Layer** – concrete implementations of repository interfaces, external service adapters, and data mapping.

This layered approach ensures that the core business logic (domain + application) has zero dependencies on delivery mechanisms or databases. It can be unit‑tested without any infrastructure.

### 14.2 Module Structure (Representative: Sales Module)

To illustrate the internal anatomy of a module, we use the **Sales** module as an example. All other core modules follow the same pattern.

```
sales/
├── api/                  (Interface Layer)
│   └── sales_controller.dart
├── application/          (Application Layer)
│   ├── sales_service.dart
│   └── payment_service.dart
├── domain/               (Domain Layer)
│   ├── entities/
│   │   └── sale.dart
│   ├── value_objects/
│   │   ├── invoice_number.dart
│   │   └── money.dart
│   ├── repositories/
│   │   └── sale_repository.dart  (abstract interface)
│   ├── services/               (domain services, if any)
│   │   └── discount_calculator.dart
│   └── events/
│       └── sale_completed.dart
├── infrastructure/       (Infrastructure Layer)
│   ├── repositories/
│   │   └── sale_repository_impl.dart
│   └── mappers/
│       └── sale_mapper.dart
└── sales_module.dart           (module registration, DI)
```

**Layer Responsibilities:**

- **`api/`**: The `SalesController` is a shelf `Handler` that deserializes HTTP requests, validates input using the domain model, calls the application service, and serialises the response. It knows about HTTP but not about the database or business rules.

- **`application/`**: `SalesService` is the entry point for all sales use‑cases (`createSale`, `voidSale`, `processReturn`, `addPayment`). It orchestrates the workflow: it opens a database transaction (via an injected `UnitOfWork` or `Database` interface), calls domain services for calculations, interacts with other module services via interfaces (e.g., `InventoryService`, `AccountingService`, `CustomerService`), and persists the sale through the repository. The service is technology‑agnostic; it receives and returns domain objects.

- **`domain/`**: Contains the `Sale` aggregate root, `SaleItem` entity, `Money` value object (with currency), and the `SaleRepository` abstract interface (`save`, `findById`, `findAll`). It also contains pure domain services like `DiscountCalculator` that apply business rules without side effects.

- **`infrastructure/`**: `SaleRepositoryImpl` implements the repository interface using SQLite (via `sqflite`). It translates domain objects to database rows and vice versa using mappers. This layer also contains the concrete implementations of interfaces from other modules that the Sales module depends on, if they are not provided by the other module’s own infrastructure.

### 14.3 Cross‑Module Interaction & Dependency Inversion

Modules do not directly reference each other’s concrete classes. Instead, they depend on **abstract interfaces** (contracts). For example, `SalesService` depends on:

```dart
abstract class InventoryService {
  Future<Map<int, double>> deductStock(TransactionContext txn, List<SaleItem> items, int warehouseId);
  Future<void> restock(TransactionContext txn, List<SaleReturnItem> items);
}

abstract class AccountingService {
  Future<void> postSale(TransactionContext txn, Sale sale, Map<String, double> context);
  Future<void> postSalesReturn(TransactionContext txn, SalesReturn ret);
}

abstract class CustomerService {
  Future<void> updateLoyaltyPoints(TransactionContext txn, int customerId, double amount);
  Future<Customer?> findById(int customerId);
}
```

The `Inventory` module provides an implementation of `InventoryService`; the `Accounting` module provides `AccountingService`, and so on. At application startup, the Dependency Injection (DI) container wires the actual implementations to these interfaces. The Sales module never knows or cares which concrete class is behind the interface.

This pattern allows:
- **Testability:** In unit tests, mock or stub implementations are injected into `SalesService`, enabling fast, isolated testing of business logic.
- **Replaceability:** If the inventory calculation algorithm changes (e.g., from FIFO to weighted average), only the `InventoryService` implementation changes; the Sales module is unaffected.
- **Business‑Type Extensibility:** A specialised pharmacy sales service can extend the core `SalesService` and override certain behaviours, while still depending on the same interfaces.

### 14.4 The Service Layer and Transaction Management

The Application Layer services are stateless and do not hold database connections. They receive a `TransactionContext` (or a `Database` object) that represents the current transactional scope. This context is created by the infrastructure layer (e.g., an HTTP middleware that opens a database transaction for the request, or a higher‑level service that orchestrates a unit of work).

The typical flow for a command (e.g., `createSale`) is:

1. The controller receives the HTTP request and calls `SalesService.createSale(saleData, txnContext)`.
2. The service validates the domain rules, calls `InventoryService.deductStock(txnContext, …)` (which reads and writes within the same transaction), calls `AccountingService.postSale(txnContext, …)`, and calls `CustomerService.updateLoyaltyPoints(txnContext, …)`.
3. The service calls `saleRepository.save(txnContext, sale)` to persist the Sale aggregate.
4. If any step throws an exception, the transaction is rolled back. The controller catches the exception and returns an appropriate HTTP error.

In the current local‑server implementation, the database transaction is managed via the `sqflite` `Transaction` object, which is passed through the call chain. This provides ACID guarantees locally. For future cloud‑native or distributed scenarios, the transaction boundary could be redefined using a saga pattern, but the service interface remains unchanged.

### 14.5 Module Registration & Composition Root

All modules are assembled in a **composition root** during application bootstrap. Each module exposes a registration function (e.g., `SalesModule.register(Container container)`) that binds its interfaces to their implementations and registers its API routes.

```dart
class SalesModule {
  static void register(Container container, Router router) {
    // Domain
    container.registerSingleton<DiscountCalculator>(DefaultDiscountCalculator());
    // Infrastructure
    container.registerSingleton<SaleRepository>(SaleRepositoryImpl(container<Database>()));
    // Application
    container.registerSingleton<SalesService>(SalesServiceImpl(
      container<SaleRepository>(),
      container<InventoryService>(),
      container<AccountingService>(),
      container<CustomerService>(),
    ));
    // API
    router.mount('/api/sales', SalesController(container<SalesService>()).router);
  }
}
```

The container ensures that `InventoryService` and `AccountingService` are already registered by their respective modules before `SalesModule` is initialised. The registration order is: core infrastructure (database, server) → domain services (inventory, accounting) → application services (sales, purchase) → API controllers.

### 14.6 Business‑Type Conditional Registration

Modules that are business‑type specific (e.g., `PharmacyModule`, `EducationModule`) are only registered if the active business type manifest includes them. The `ConfigurationService` reads the manifest, and the composition root iterates over the `activeModules` list, conditionally calling the registration functions.

```dart
if (config.activeModules.contains('pharmacy')) {
  PharmacyModule.register(container, router);
}
```

If a module is not registered, its API routes are absent, and any attempt by a generic module to call its interface (e.g., `InventoryService` trying to call a pharmacy‑specific drug check) will fail gracefully because the interface implementation will be a no‑op or throw an `UnsupportedFeatureException`, which is caught and reported.

### 14.7 Key Modules and Their Interfaces

A summary of the core domain modules and their primary responsibilities:

| Module | Core Aggregates | Key Service Interfaces (Ports) | Offered Services (Adapters) |
|--------|-----------------|-------------------------------|----------------------------|
| **Inventory** | Stock, Batch, StockMovement | `InventoryService` (deduct, restock, transfer, adjust), `StockQueryService` (reports) | FIFO deduction engine, batch expiry checker |
| **Accounting** | JournalEntry, Account, PostingTemplate | `AccountingService` (post journal, reverse), `LedgerQueryService` | Double‑entry posting engine, trial balance generator |
| **Customer** | Customer, CustomerGroup | `CustomerService` (loyalty, credit check), `CustomerQueryService` | Customer ledger, loyalty point calculator |

| **Products** | Product, Category, Brand, Unit | `ProductService` (CRUD, barcode lookup), `ProductQueryService` | Product search, variant resolution |
| **Sales** | Sale, SaleItem, SalePayment | (consumes Inventory, Accounting, Customer) | POS orchestration, return processing, installment |
| **Purchase** | Purchase, PurchaseItem, SupplierPayment | (consumes Inventory, Accounting, Supplier) | Purchase orchestration, order conversion |
| **Reports** | Various read‑only projections | `ReportService` (sales report, stock report, p&l) | Pre‑computed aggregates, Excel/PDF export |

### 14.8 Event‑Driven Communication (Internal)

Within a module, direct method calls are used. Across modules, communication is primarily synchronous (orchestrated by the application service) because most operations require transactional consistency (e.g., a sale must atomically deduct inventory and post accounting entries). However, for non‑transactional, asynchronous side effects, the system uses a lightweight **internal event dispatcher**.

- `EventBus` is a simple in‑memory publish/subscribe mechanism within the local server process.
- After a sale is completed and the transaction committed, `SalesService` publishes a `SaleCompleted` event.
- Subscribers (registered during module init) react: the notification service sends an SMS receipt, the loyalty service updates cumulative points, the analytics service updates dashboard counts.
- These subscribers execute outside the original transaction boundary, so failures in notification do not roll back the sale.

This approach keeps the core transaction lean while enabling extensibility. The event bus is synchronous by default (to keep things simple) but can be made asynchronous via a microtask queue if needed. All events are also recorded in the `change_log` for sync purposes.

### 14.9 The Plugin Manager as a Component

The Plugin Manager, introduced in Integration Architecture, is itself a component registered in the composition root. It scans a directory (or a built‑in registry) for classes that implement specific plugin interfaces (`PaymentGatewayPlugin`, `PrinterPlugin`, etc.). It provides a registry from which other modules can obtain the currently active plugin by type.

Plugins are implemented as separate Dart packages that depend on the core domain interfaces. They are compiled into the application (no dynamic loading in the mobile sense) but only instantiated if configured. This gives the benefits of static analysis and tree‑shaking while maintaining a clean separation.

### 14.10 Code Generation and Boilerplate Reduction

To keep the component code lean, the project uses code generation for:
- **Immutable value objects:** `freezed` for `Money`, `InvoiceNumber`, entity states.
- **JSON serialization:** `json_serializable` for API DTOs and sync payloads.
- **Repository stubs:** Custom annotations generate the basic CRUD SQL queries for simple entities, reducing repetitive SQLite code.

These generators are run as part of the build process, keeping the manually written code focused on business logic.

## 15. API & Service Contracts

The Amar Hisab architecture exposes its capabilities through a set of clearly defined, versioned service contracts. These contracts govern communication between the mobile/desktop clients and the local server, between the local server and the optional cloud sync service, and between external users (students, parents) and the Public Portal. A rigorous approach to API design ensures that all components – even those operating offline – can reliably interact, that integrations are stable, and that the system can evolve without breaking existing deployments.

### 15.1 Design Principles

- **Contract‑First:** API contracts are defined before implementation. For REST, OpenAPI 3.0 specifications are maintained. For gRPC, Protocol Buffer (`.proto`) files are the source of truth. These contracts are stored in the `api/` directory of the monorepo and are the basis for client‑ and server‑code generation.
- **Simplicity & Consistency:** The local API uses straightforward REST with JSON because it is easy to debug, test manually, and integrate with lightweight HTTP clients. The cloud sync API uses gRPC for its performance, streaming, and strongly typed contracts.
- **Backward Compatibility:** The local server and client must remain compatible across version upgrades (a user may update the server but not all client devices immediately). The API versioning strategy is designed to support this. The cloud sync protocol maintains backward compatibility for at least one major version to allow gradual rollout.
- **Offline‑First:** The API does not guarantee immediate availability of cloud‑originated data. Clients treat the local server as the authoritative source and implement optimistic UI and local caching. No API endpoint blocks indefinitely waiting for a network response.
- **Least Privilege:** Every API endpoint requires authentication and enforces the role‑based permissions described in Section 10. The contract includes the required permission for each endpoint.

### 15.2 API Taxonomy

Amar Hisab defines three distinct API surfaces:

| API Surface | Audience | Protocol | Transport |
|-------------|----------|----------|-----------|
| **Internal API** | Amar Hisab clients (Flutter mobile/desktop/web) and the local server’s own admin UI. | REST/JSON over HTTP | Local network (LAN) |
| **Public Portal API** | Unauthenticated external users (students, parents, customers) accessing self‑service features via a web browser. | REST/JSON over HTTP | Local network, accessed via QR‑coded URLs |
| **Cloud Sync API** | The local server (or standalone mobile) communicating with the Cloud Sync Service. | gRPC with Protocol Buffers | Internet (TLS 1.3) |

The Internal API and Public Portal API are served by the same local shelf HTTP server, but on different path prefixes (`/api/` vs. `/public/`) and with different authentication middleware.

### 15.3 REST API Conventions (Internal & Public)

All REST endpoints adhere to the following conventions to ensure a predictable developer experience.

**URL Structure:**  
`http://{host}:8080/api/v1/{resource}`  
Example: `http://amarhisab.local:8080/api/v1/sales`

**HTTP Methods:**
- `GET` – Retrieve a resource or collection.
- `POST` – Create a new resource.
- `PUT` – Fully update an existing resource (idempotent).
- `PATCH` – Partially update a resource (for supported fields).
- `DELETE` – Soft‑delete or deactivate a resource (physical delete is extremely rare).

**Status Codes:**
- `200 OK` – Successful GET, PUT, PATCH.
- `201 Created` – Successful POST, with a `Location` header for the new resource.
- `204 No Content` – Successful DELETE, or an operation with no response body.
- `400 Bad Request` – Invalid input; the response body contains a detailed error message.
- `401 Unauthorized` – Missing or invalid authentication token.
- `403 Forbidden` – Valid credentials but insufficient permissions.
- `404 Not Found` – Resource does not exist.
- `409 Conflict` – Business rule violation (e.g., duplicate invoice number, insufficient stock).
- `422 Unprocessable Entity` – Semantic validation failure (e.g., unbalanced journal entry).
- `429 Too Many Requests` – Rate limiting (used by cloud, but also locally configurable).
- `500 Internal Server Error` – Unexpected failure.

**Request & Response Format:**  
All `POST`, `PUT`, and `PATCH` bodies are JSON. All successful responses (`200`, `201`) return JSON. The top‑level response envelope is:
```json
{
  "success": true,
  "data": { ... },      // for single resource or operation result
  "meta": { ... }       // for collections: pagination info
}
```
Error responses:
```json
{
  "success": false,
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "Insufficient stock for product Napa Extra (requested: 5, available: 3).",
    "details": { ... }
  }
}
```
This envelope allows clients to uniformly handle responses.

**Pagination:**  
Collection endpoints (e.g., `GET /sales`) support cursor‑based pagination via query parameters:
- `limit` (default 20, max 100)
- `cursor` (opaque string, returned in `meta.next_cursor` of a previous response)

The `meta` object includes:
```json
{
  "next_cursor": "eyJpZCI6MTIzfQ==",
  "has_more": true,
  "total_count": 250  // optional, may be omitted for performance
}
```

**Filtering & Sorting:**  
Standard query parameters:
- `?status=Completed,Draft` – filter by field value (comma‑separated for multiple).
- `?from_date=2026-07-01&to_date=2026-07-15` – date range.
- `?customer_id=42` – foreign key filter.
- `?sort=-created_at` – sort by field; prefix `-` for descending.

**Error Detail Codes:**  
A set of machine‑readable error codes (like `INSUFFICIENT_STOCK`, `DUPLICATE_INVOICE`, `UNBALANCED_JOURNAL`, `INVALID_CREDENTIALS`) allows clients to implement specific recovery logic or user messages without parsing human‑readable strings.

### 15.4 Authentication & Authorization on API

**Internal API:**  
All endpoints (except `/api/v1/auth/login`) require an `Authorization: Bearer <JWT>` header. The local JWT is issued by the local server’s auth endpoint and contains claims: `user_id`, `role`, `business_id`, `device_id`. A shelf middleware validates the token on every request, extracts the claims, and attaches a `Principal` object to the request context. The controller or an authorization middleware then checks the required permission (e.g., `sale:create`) against the role’s permission set. The mapping of endpoints to required permissions is declared declaratively in the API specification.

**Public Portal API:**  
Endpoints under `/public/v1/` use a different authentication model. They require either:
- A valid **portal token** (embedded in the QR code URL), which grants read access to a specific student’s or customer’s own data. The token is verified against the `customer_tokens` table.
- Or a **student ID + portal secret** (for the public portal login flow), which after verification returns a short‑lived session token used for subsequent requests.
No global user authentication is required.

**Cloud Sync API:**  
Uses mTLS with device certificates or a device‑specific JWT issued by the cloud. The cloud service validates the tenant and device identity on every gRPC call.

### 15.5 Versioning Strategy

REST APIs are versioned via a URL path prefix (`/api/v1/`, `/api/v2/`). The version number changes only when backwards‑incompatible changes are introduced (removing a field, changing a field type, removing an endpoint). Additive changes (new endpoints, new optional fields) do not require a version bump. The local server may support multiple API versions simultaneously during a migration period; the `v1` routes redirect to the new implementation where possible. Clients specify the version they wish to use; after a grace period, old versions are deprecated and eventually removed.

gRPC services use Protocol Buffer’s native backward‑compatibility rules: fields are never removed or renumbered; new fields are added with new numbers. Service methods are not removed; instead, a new service version is added (e.g., `SyncServiceV2`) and the old one is maintained until all clients are updated. The `package` name and service name can incorporate a major version to keep old and new implementations side‑by‑side in the same server binary.

### 15.8 Cloud Sync API (gRPC)

The cloud sync protocol is defined in the `sync.proto` file. It is a bidirectional, asynchronous event‑driven contract.

#### 15.8.1 Proto Service Definition (Excerpt)

```protobuf
syntax = "proto3";
package amarhisab.sync.v1;

service SyncService {
  // Push a batch of local changes to the cloud.
  rpc PushBatch(PushBatchRequest) returns (PushBatchResponse);

  // Pull remote changes since the last known sequence.
  rpc PullChanges(PullRequest) returns (stream ChangeEvent);

  // (Future) Bidirectional stream for real-time sync
  rpc SyncStream(stream ChangeEvent) returns (stream ChangeEvent);
}

message PushBatchRequest {
  string device_id = 1;
  int64 last_synced_sequence = 2;
  repeated ChangeEvent changes = 3;
}

message ChangeEvent {
  string change_id = 1;        // UUID
  string entity_type = 2;
  int64 entity_id = 3;
  string operation = 4;        // "INSERT", "UPDATE", "DELETE"
  bytes payload = 5;          // JSON serialized entity
  bytes old_values = 6;        // JSON, for updates/deletes
  int64 timestamp_ms = 7;
  int64 sequence = 8;          // device-local sequence number
  string device_id = 9;
}
// ...
```

#### 15.8.2 Push/Pull Semantics

- **Push:** The local server sends a batch of `ChangeEvent` records, ordered by device‑local sequence number. The cloud processes them in order, applies merging and conflict resolution, and acknowledges the highest sequence number successfully stored. The response may include conflict notifications if manual intervention is required.
- **Pull:** The local server requests changes since `last_remote_sequence`. The cloud streams `ChangeEvent` records in global sequence order. The local server applies them to its database. The stream ends when all available changes are sent; the connection remains open for a short period to allow batching of near‑future changes (long‑lived streaming is a future enhancement).

#### 15.8.3 Idempotency & Deduplication

The `change_id` is a globally unique UUID. The cloud maintains a set of seen `change_id`s per device (with TTL) and ignores duplicates. This allows the local server to safely retry pushes after a network error. The `PushBatchResponse` includes the `accepted_sequence`, so the local server knows exactly which sequence was last committed, even if a later batch was partially processed before a crash.

### 15.9 API Documentation & Tooling

- **OpenAPI 3.0:** The internal REST API is fully described in an `openapi.yaml` file, auto‑generated from code annotations (using `swagger_parser` or similar Dart tools) and manually curated. This file is served by the local server at `/api/docs` via Swagger UI, providing an interactive reference for developers and power users.
- **Protocol Buffers:** The gRPC service definitions are the canonical source. Generated documentation (using `protoc-gen-doc`) is published alongside each release.
- **Postman Collections:** A maintained Postman collection covering all internal and public endpoints is provided to aid manual testing and integration.
- **Changelog:** Every release includes a contract changelog highlighting additions, deprecations, and removals.

### 15.10 Client SDK Generation

To reduce integration friction, the Flutter client (and any future third‑party integrations) consume the API contracts through generated code:

- **Dart REST Client:** The OpenAPI specification is used to generate a Dart HTTP client (using `openapi_generator` or `swagger_dart_code_generator`). This client provides typed request/response objects, enums, and endpoint methods, eliminating manual JSON parsing and string‑based URL construction.
- **gRPC Client:** The `.proto` files generate Dart gRPC client stubs (using `protoc-gen-dart`) for the sync client in the local server. The generated code handles serialization and connection management.
- **Public Portal JavaScript:** For the public portal web UI, a minimal JavaScript fetch‑based wrapper is generated from the same OpenAPI spec, ensuring the web portal stays in sync with the API.

By treating the API contracts as the foundation, we ensure that all parts of the system – server, client, cloud, and web portal – are speaking the same language, reducing integration bugs and accelerating feature development.

## 16. Event & Message Architecture

The behaviour of Amar Hisab is driven not only by direct user commands but also by reactions to significant occurrences within the system – a sale is completed, a stock level drops below its reorder point, a student’s fee installment becomes overdue. The Event & Message Architecture provides a structured, decoupled mechanism for capturing these occurrences, propagating them to interested internal consumers, and, when necessary, transmitting them to the cloud for distributed synchronisation. This architecture reinforces the modularity of the system by ensuring that a module can announce a fact without needing to know which other modules, if any, will act upon it.

### 16.1 Types of Events

The system distinguishes two fundamental categories of events:

| Category | Scope | Purpose | Examples |
|----------|-------|---------|----------|
| **Domain Events (Internal)** | Within the local server process | Notify other in‑process modules of a business fact that has occurred, so they can execute side‑effects (notifications, loyalty updates, dashboard refresh) without the originating module depending on them. | `SaleCompleted`, `PaymentReceived`, `StockLow`, `StudentEnrolled` |
| **Sync Events (External)** | Between local server and cloud sync service | Capture data mutations that must be replayed on other devices or persisted to the cloud event ledger for eventual consistency. | Any `change_log` entry (`sale:INSERT`, `product:UPDATE`, `stock_movement:INSERT`) |

Domain events are high‑level, business‑meaningful facts. Sync events are low‑level, data‑centric change records. They are closely related but serve different architectural roles. A single domain event may result in multiple sync events (e.g., a sale completion produces a `sale` INSERT, multiple `stock_movement` INSERTs, and a `journal_entry` INSERT). The internal event bus handles domain events; the sync engine handles sync events.

### 16.2 Internal Event Bus

The internal event bus is an in‑memory, lightweight publish‑subscribe mechanism that operates within the local server process. It is deliberately simple: no external message broker, no persistence, no distributed guarantees. Its sole responsibility is to decouple modules within the same process.

**Interface:**
```dart
abstract class EventBus {
  void publish<T extends DomainEvent>(T event);
  Stream<T> on<T extends DomainEvent>();
}
```

The `EventBus` is a singleton registered in the dependency injection container. Any module can inject it and either publish events or subscribe to streams of specific event types.

**Implementation:**
The concrete implementation uses Dart’s `StreamController` with broadcast streams. Events are dispatched synchronously to all subscribers when `publish` is called. This means that all side‑effects triggered by a domain event execute within the same microtask queue as the publisher. While this is simple and sufficient for most cases (notification queuing, analytics logging), caution is taken to avoid long‑running operations blocking the event loop. Subscribers are expected to offload heavy work (e.g., sending an SMS) to an asynchronous background worker.

**Transactional Safety:**  
Domain events are published **after** the database transaction that produced them is committed. Publishing within the transaction risks that a subscriber reads uncommitted data, or that a subscriber’s failure rolls back the core business operation. Therefore, the application service collects domain events from the aggregate during the transaction, and once the transaction is successfully committed, it publishes them to the bus. This pattern ensures at‑least‑once delivery of events to in‑process subscribers (in the rare case of a process crash between commit and publish, events may be lost, but this is acceptable for the side‑effect use cases; critical data propagation is handled by the sync engine).

### 16.3 Domain Events Catalog

Domain events are immutable, serializable Dart objects that represent a past occurrence. They are named in the past tense and carry the minimum data necessary for consumers to act.

**Example Domain Events:**

```dart
class SaleCompleted extends DomainEvent {
  final int saleId;
  final String invoiceNumber;
  final int customerId;
  final double grandTotal;
  final double paidAmount;
  final DateTime completedAt;
}

class PaymentReceived extends DomainEvent {
  final int saleId;
  final int paymentId;
  final double amount;
  final String method;
}

class StockLow extends DomainEvent {
  final int productId;
  final int warehouseId;
  final double currentQuantity;
  final double threshold;
}

class StudentEnrolled extends DomainEvent {
  final int studentId;
  final int batchId;
  final DateTime enrollmentDate;
}
```

Each domain event class extends a base `DomainEvent` class that includes a unique `eventId` (UUID), a `timestamp`, and the `businessId` of the originating tenant. This allows future tracing and potential cross‑process propagation if needed.

### 16.4 Subscribers and Cross‑Module Reactions

Modules subscribe to events they are interested in during their registration phase. This is where cross‑module coordination happens without direct coupling.

**Example: Notifications Module subscribes to `SaleCompleted`:**
```dart
class NotificationService {
  NotificationService(EventBus eventBus, SmsService smsService) {
    eventBus.on<SaleCompleted>().listen((event) {
      _onSaleCompleted(event);
    });
  }

  void _onSaleCompleted(SaleCompleted event) {
    // Queue an SMS receipt to the customer (if opted in)
    // This runs asynchronously; failure does not affect the sale.
  }
}
```

**Example: Loyalty Module subscribes to `PaymentReceived`:**
```dart
class LoyaltyService {
  LoyaltyService(EventBus eventBus) {
    eventBus.on<PaymentReceived>().listen(_onPaymentReceived);
  }

  void _onPaymentReceived(PaymentReceived event) {
    // Update customer loyalty points based on amount.
    // Runs in a separate database transaction.
  }
}
```

**Example: Dashboard Module subscribes to multiple events to invalidate its caches:**
```dart
class DashboardCache {
  DashboardCache(EventBus eventBus) {
    eventBus.on<SaleCompleted>().listen((_) => invalidate('sales'));
    eventBus.on<StockLow>().listen((_) => invalidate('low_stock'));
  }
}
```

This publish‑subscribe model makes it trivial to add new behaviours (e.g., an audit log emailer, a push notification to the owner’s mobile) without modifying the Sales or Payment modules. Each new feature simply becomes a new subscriber.

### 16.5 Event‑to‑Sync‑Log Bridge

Domain events and sync events are connected by a bridge component: the `ChangeLogRecorder`. This component subscribes to a selected set of domain events and translates them into the corresponding `change_log` entries that the sync engine uses.

**Flow:**
1. A business operation (e.g., sale) completes, the domain event `SaleCompleted` is published.
2. The `ChangeLogRecorder` receives the event. It knows that a sale implies several data changes. It queries the just‑committed sale aggregate (via repository) to get the exact state.
3. It inserts `change_log` rows: one for `sales` (INSERT), multiple for `stock_movements`, one for `journal_entries`.
4. These `change_log` rows are now queued for the sync engine to push to the cloud.

This bridge design keeps the sync logic separate from the business modules. The sync engine does not need to understand domain events; it only deals with the `change_log` table. The mapping from domain events to data changes is encapsulated in the recorder, which can be tested independently.

### 16.6 Transactional Outbox for Reliable Sync

A critical requirement is that no data mutation is ever committed without a corresponding sync event being persisted. The architecture ensures this through the **Transactional Outbox** pattern.

Instead of the `ChangeLogRecorder` writing to the `change_log` table *after* the transaction (which could fail or the process could crash), the application service **directly writes** the `change_log` entries within the same database transaction that persists the business data.

```dart
await database.transaction((txn) async {
  // Save sale, items, payments
  final saleId = await txn.insert('sales', sale.toMap());
  // ... save items, payments ...

  // Record change_log entries inside the same transaction
  await txn.insert('change_log', ChangeLogEntry(
    entityType: 'sale',
    entityId: saleId,
    operation: 'INSERT',
    payload: jsonEncode(sale.toJson()),
    deviceId: deviceId,
    businessId: sale.businessId,
    // ...
  ).toMap());
});
```

By doing this, the `change_log` record is guaranteed to exist if and only if the business data exists. There is no risk of an event being missed due to a crash between transaction commit and event publication. The sync engine simply polls the `change_log` table for pending entries.

Domain events (`SaleCompleted`, etc.) are still published after commit for in‑process subscribers, but the authoritative sync trail is the `change_log` table written atomically with the data.

### 16.7 Event Versioning

Domain event classes are versioned so that the system can evolve without breaking subscribers that may still expect older event shapes.

- Each event class carries a `version` field (e.g., `1`). When a new field is added, the version is incremented.
- The `EventBus` dispatches the event to all subscribers. Subscribers that are aware of the new version can cast to the appropriate type. Legacy subscribers simply use the original base type or ignore the new fields.
- For sync events, the `payload` in the `change_log` includes a `schema_version` field. The cloud and other devices can use this to apply appropriate transformations if they are on a different software version. The system maintains a set of upcasters that transform older payload versions to the latest before processing.

This approach avoids the need for all devices to be updated simultaneously, which is a critical property for an offline‑first product where devices may run different versions for extended periods.

### 16.8 External Event Integrations (Future)

While the internal event bus is purely local, the event architecture is designed to accommodate future integration with external message brokers (e.g., RabbitMQ, Kafka) for advanced enterprise deployments. In such a scenario, a `CloudEventPublisher` subscriber would listen to selected domain events and publish them to a cloud‑based event mesh, enabling webhooks, real‑time analytics dashboards, and integration with third‑party systems. This is a forward‑looking design decision; the current implementation only requires the local event bus.

### 16.9 Summary

The Event & Message Architecture enables Amar Hisab to be both reactive and extensible. Domain events decouple modules within the local process, allowing side‑effects like notifications and dashboard updates to be added independently. The transactional outbox pattern, combined with the `change_log` table, provides a rock‑solid foundation for the sync engine, guaranteeing that every data change is captured and ready for propagation without any risk of loss. This dual‑channel approach – in‑memory events for immediate, non‑critical reactions, and persisted change logs for durable, synchronisable facts – balances flexibility with reliability.

## 17. Quality Attributes & Trade‑offs

Architecture is the art of balancing competing forces. Amar Hisab’s mission—to provide a free, offline‑first, multi‑vertical business operating system that runs on modest hardware—imposes a unique set of constraints. This section analyses the key quality attributes (non‑functional requirements) that the system must satisfy, evaluates how the architectural decisions address them, and honestly documents the trade‑offs that were made. Understanding these trade‑offs is essential for the engineering team to make informed decisions as the system evolves.

### 17.1 Performance

**Goal:** POS transactions must complete within 2 seconds end‑to‑end on reference hardware; product searches and report generation must feel instantaneous.

**Architectural Response:**
- All primary data resides in an embedded SQLite database on the local machine, eliminating network latency for reads and writes.
- The FIFO stock deduction algorithm is implemented as a single optimised SQL query within the sale transaction, avoiding multiple round‑trips.
- The client uses local caching (product list, customer list) to reduce lookups during POS.
- The local HTTP server is lightweight (Dart `shelf`) and handles requests asynchronously.

**Trade‑off:**
- **SQLite’s single‑writer limitation** means that extremely high concurrent write loads (e.g., dozens of POS terminals all finalising sales simultaneously) could encounter lock contention. In practice, a single shop with 1–20 clients does not reach this threshold; WAL mode mitigates read‑while‑write blocking. If a business grows beyond a single server’s capacity, the architecture recommends deploying multiple local servers per department rather than over‑engineering the single‑server solution.

### 17.2 Scalability

**Goal:** The system must scale from a single smartphone to a multi‑branch chain with centralised reporting.

**Architectural Response:**
- The local system scales vertically: a modern desktop can handle 20+ concurrent clients without degradation. For larger branches, multiple local servers can be deployed, synchronising via the cloud.
- The cloud sync service is designed for horizontal scaling: stateless gateway pods and a partitioned PostgreSQL database.
- The optional cloud component ensures that infrastructure cost scales with revenue (sync subscribers).

**Trade‑off:**
- **The local server is not a distributed system.** To maintain simplicity and offline‑first reliability, we deliberately avoided building a peer‑to‑peer mesh of devices within a branch. This means a branch relies on a single local server (or a few independent servers). If that server fails, local operations are interrupted until it is restored. The mitigation is the fast restore process (<15 minutes from backup) and the availability of cheap, reliable hardware for the server role. We accept this single point of failure in exchange for drastic reductions in complexity and the elimination of distributed consensus problems in the core transaction path.

### 17.3 Reliability & Availability

**Goal:** The system must be usable even when internet is unavailable; data loss must be minimised.

**Architectural Response:**
- The offline‑first design means that all core functions operate without any internet connectivity. The local SQLite database is the source of truth.
- Backup is multi‑layered: local file, Google Drive, Telegram. The sync engine provides an additional copy in the cloud.
- The transactional outbox pattern ensures that every data mutation is atomically recorded in the change log, preventing sync gaps.

**Trade‑off:**
- **Immediate consistency across branches is sacrificed for offline autonomy.** A sale made in Branch A is not instantly visible in Branch B; it is visible only after both branches have synced with the cloud. For most small businesses, this is perfectly acceptable; inter‑branch real‑time stock visibility is a nice‑to‑have, not a day‑to‑day necessity. We chose not to implement a real‑time distributed database, which would have been incompatible with offline operation and low‑bandwidth environments.

### 17.4 Security

**Goal:** Protect sensitive financial and personal data, enforce role‑based access, and provide an immutable audit trail.

**Architectural Response:**
- Authentication is JWT‑based; passwords are hashed with Argon2id. RBAC is enforced at the API middleware level.
- Data at rest is optionally encrypted via SQLCipher; cloud data is encrypted in transit (TLS 1.3) and at rest.
- The `audit_log` table is append‑only, providing a tamper‑resistant record of all mutations.

**Trade‑off:**
- **Local network communication is HTTP by default, not HTTPS.** Requiring every small shop to install and manage TLS certificates would create an insurmountable support burden and conflict with the zero‑training goal. We mitigate this by recommending a secure Wi‑Fi network and offering an optional certificate pinning mode for security‑conscious users. We accept that in the default mode, a sophisticated attacker on the same local network could theoretically intercept traffic, but the threat model for a typical grocery shop in Bangladesh does not justify the usability cost.
- **The “Remember Me” feature on trusted devices** reduces security in favour of speed. For single‑user micro‑shops, entering a password on every transaction would be a major friction point. We enable this convenience feature with clear warnings and recommend that multi‑user setups enforce per‑transaction authentication for sensitive operations.

### 17.5 Usability & Simplicity

**Goal:** A shop owner with minimal technical literacy should be able to install and use the system without external help.

**Architectural Response:**
- One‑click installer, automatic mDNS discovery, pre‑configured business type templates, and a Bengali‑first UI.
- The public portal allows students/customers to self‑serve via QR codes, reducing staff workload.
- All complex processes (FIFO, double‑entry accounting) are fully automated behind the scenes.

**Trade‑off:**
- **Advanced configuration is hidden or absent in the standard UI.** For example, customising the Chart of Accounts or creating new posting templates is not exposed to the average user; it requires an “Accountant” role or is reserved for enterprise customisation. This keeps the interface clean for 95% of users but means that power users may initially find the system inflexible. We accept this because adding a “simple/advanced” toggle would increase development and testing complexity, and the target market overwhelmingly prefers simplicity over configurability.
- **The offline‑first nature means some cloud‑era conveniences are not present.** Features like real‑time collaborative editing of an invoice across devices are impossible in an offline model. We consciously limit the feature set to what works reliably offline.

### 17.6 Maintainability & Extensibility

**Goal:** The system must be modifiable to support new business types and integrations with minimal core code changes.

**Architectural Response:**
- Modules are decoupled via dependency inversion and share common abstractions. New business types are added via declarative manifests.
- The plugin architecture allows new payment gateways, SMS providers, and printers to be integrated without altering the core.
- Code generation reduces boilerplate, keeping manual code focused on business logic.

**Trade‑off:**
- **The single codebase for all business types increases the compilation size** and, in theory, the attack surface. A dedicated pharmacy build would be smaller and “cleaner” than one that also contains grocery and education code. However, maintaining separate builds for each vertical would lead to a combinatorial explosion of testing and release management. We accept the larger binary size (which is still modest by modern standards) in exchange for vastly simplified CI/CD and a unified codebase that can be maintained by a lean team.
- **The heavy use of code generation and dependency injection** adds a learning curve for new developers. The onboarding cost is offset by the long‑term reduction in bugs and faster feature development.

### 17.7 Data Consistency & Integrity

**Goal:** Financial data must be accurate and auditable; inventory counts must reflect reality.

**Architectural Response:**
- Double‑entry accounting is enforced at the application level with database constraints preventing unbalanced entries.
- Stock is event‑sourced: the current quantity is derived from the stock movement log, not stored as a mutable number.
- The transactional outbox ensures that sync events are never lost.

**Trade‑off:**
- **Event‑sourcing inventory adds query complexity and storage overhead.** Instead of a simple `UPDATE stock SET qty = qty - 5`, the system writes a new `stock_movement` row and updates a summary table. This requires more storage and slightly more complex logic. We accepted this trade‑off because it provides an unbreakable audit trail and makes synchronisation significantly simpler (immutable events are easier to merge than mutable state). For the typical inventory size (a few thousand SKUs), the storage impact is negligible.

### 17.8 Portability & Deployment

**Goal:** The system should run on as many platforms as possible without sacrificing capability.

**Architectural Response:**
- Flutter enables a single codebase for Android, iOS, Windows, macOS, Linux, and Web.
- The local server runs on the three major desktop platforms.
- The cloud service is containerised and platform‑agnostic.

**Trade‑off:**
- **Web client limitations.** The Flutter Web build does not have full access to all native APIs (Bluetooth, USB printing). For the web client, hardware integration is delegated to the local server; the web client is primarily for data entry and reporting. A dedicated desktop or mobile client is required for full POS functionality. We accept this because web deployment is not the primary target for the core POS experience; it serves as a lightweight supplement for managers or for the public portal.

### 17.9 Cost & Monetization

**Goal:** Core features must be free forever; the business must generate sustainable revenue.

**Architectural Response:**
- Feature flags and a licensing service (local + cloud‑verified) allow premium features (advanced AI reports, unlimited SMS, white‑label) to be toggled without affecting the free core.
- Revenue streams (SMS packs, payment gateway commissions, hardware reselling) are external to the core product and do not gate essential functionality.

**Trade‑off:**
- **The free‑forever model means that some users will never generate revenue.** The architecture must be efficient enough to serve these users at near‑zero marginal cost. The offline‑first design is the key: free users do not consume cloud server resources beyond occasional backup and sync (which is heavily throttled or requires separate subscription). The cost of supporting a free, offline user is essentially zero. We accept that a small percentage of users will be unprofitable, trusting that the ubiquity and word‑of‑mouth from these users will drive adoption among paying customers.

### 17.10 Summary of Key Trade‑offs

| Quality Attribute | Architectural Choice | Benefit | Sacrifice |
|-------------------|----------------------|---------|-----------|
| **Performance** | Embedded SQLite, local‑only transactions | 2‑second POS, zero network latency | Limited concurrent writes (acceptable for target scale) |
| **Consistency** | Offline‑first, eventual consistency via sync | Complete offline autonomy, no internet dependency | Real‑time cross‑branch visibility is delayed |
| **Security** | HTTP on LAN, optional TLS | One‑click setup, zero certificate management | Default local traffic is unencrypted (mitigated by secure Wi‑Fi) |
| **Simplicity** | Hidden advanced config, automated accounting | Zero‑training for 95% of users | Power users have less direct control |
| **Maintainability** | Single codebase for all business types | Lean CI/CD, unified testing | Larger binary, slightly longer build times |
| **Data Integrity** | Event‑sourced inventory, transactional outbox | Immutable audit trail, reliable sync | More storage, slightly more complex queries |
| **Portability** | Flutter for all client platforms | Single codebase | Web client has limited hardware access |

These trade‑offs are not failures; they are deliberate, documented decisions that reflect the unique priorities of Amar Hisab. As the system grows, some of these trade‑offs may be revisited. The architecture is designed to allow for that evolution—for example, adding an optional local TLS mode for security‑conscious customers, or providing an “advanced configuration” UI for power users—without requiring a fundamental re‑architecture.

## 18. Operational Architecture

Amar Hisab is a business‑critical application for its users: a shop owner relies on it to record every sale, a pharmacy trusts it with medicine expiry, an academy tracks student fees through it. The operational architecture ensures that the system can be installed, run, monitored, diagnosed, and recovered with minimal technical expertise from the end‑user, while providing sufficient diagnostic power for the Amar Hisab support team to assist when needed. The guiding principle is **self‑sufficiency with assisted support**: the system should run itself day‑to‑day, but when problems occur, it must offer clear, actionable information and a secure channel for remote help.

### 18.1 Operational Scope

The operational architecture covers three distinct deployment contexts:

| Context | Primary Operator | Support Responsibility |
|---------|-----------------|------------------------|
| **Local Server (Desktop)** | Business owner / appointed admin | Self‑service + Amar Hisab Support (optional remote) |
| **Standalone Mobile** | Business owner | Self‑service |
| **Cloud Sync Service** | Amar Hisab DevOps team | Fully managed by Amar Hisab |

The local components are designed for zero dedicated IT staff. The cloud component follows standard cloud‑native operational practices.

### 18.2 Logging Strategy

Logging is the backbone of diagnostics. Amar Hisab implements structured, leveled logging across all components.

#### 18.2.1 Log Structure

Every log entry is a JSON object with the following standard fields:

```json
{
  "timestamp": "2026-07-15T10:30:45.123Z",
  "level": "INFO",
  "module": "sales",
  "correlation_id": "abc-123-def",
  "user_id": 5,
  "business_id": 1,
  "message": "Sale completed",
  "data": { "sale_id": 200, "total": 223.96 },
  "error": null
}
```

- **correlation_id:** A unique identifier generated at the start of an API request or background job and propagated through all log entries related to that operation. This allows tracing a complete workflow (e.g., a sale that failed due to stock) across multiple modules.
- **user_id / business_id:** Included when available, to allow filtering by tenant and user for support investigations.

#### 18.2.2 Log Levels

- **DEBUG:** Verbose information for developers; disabled by default in production builds.
- **INFO:** Significant business events (sale completed, purchase saved, backup successful, sync completed). This level is enabled by default.
- **WARN:** Recoverable issues (payment gateway timeout, retry attempt, low disk space, printer offline). These may indicate a problem that the user or support should investigate.
- **ERROR:** Unrecoverable failures within a single operation (failed to save sale due to database error, invalid API response). The operation fails, but the system continues.
- **FATAL:** Critical failure that prevents the application from running (database corruption detected on startup). The application halts and presents a recovery screen.

#### 18.2.3 Log Storage and Rotation (Local)

- Logs are written to a local file in the application data directory (`logs/amarhisab.log`).
- A rotating file appender is used: maximum file size 10 MB, up to 10 rotated files retained (`amarhisab.log.1`, `amarhisab.log.2`, ...). The oldest is deleted when the maximum count is exceeded.
- Log files are plain JSON lines, easily consumable by log analysis tools.
- On the local server, an in‑memory buffer of the last 1000 log entries is also maintained for quick viewing via the built‑in diagnostic dashboard (Settings → Help → View Logs).

#### 18.2.4 Remote Log Streaming (Opt‑in)

For assisted support, the user can enable temporary remote log streaming. When enabled:
- The local server opens a secure WebSocket connection to the Amar Hisab Support Cloud.
- Log entries (filtered to INFO and above, and redacting any sensitive customer data) are streamed in real‑time to a support dashboard.
- The streaming session has a time limit (default 30 minutes) and can be terminated by the user at any time.
- This feature is disabled by default and requires explicit user consent per session. It is designed for troubleshooting complex issues that cannot be resolved via screenshots or offline log files.

### 18.3 Local Health Monitoring

The local server continuously monitors its own health and the health of its connected peripherals. This information is exposed to the admin through a simple dashboard and, when critical, through in‑app notifications.

#### 18.3.1 Health Check Endpoints

The local server exposes a `/api/v1/health` endpoint (authenticated, admin only) that returns a comprehensive status report:

```json
{
  "status": "healthy",        // "healthy", "degraded", "unhealthy"
  "uptime_seconds": 86400,
  "version": "1.3.2",
  "checks": {
    "database": { "status": "healthy", "size_mb": 15.3, "integrity": "ok" },
    "disk_space": { "status": "healthy", "free_mb": 50000 },
    "sync": { "status": "online", "pending_changes": 5, "last_sync": "2026-07-15T10:25:00Z" },
    "printer": { "status": "offline", "name": "Receipt Printer", "error": "Disconnected" },
    "backup": { "status": "healthy", "last_success": "2026-07-15T03:00:00Z" }
  }
}
```

- **database:** Runs `PRAGMA integrity_check` and reports the database file size.
- **disk_space:** Checks available space on the volume where the database resides; warns if below a threshold (1 GB).
- **sync:** Checks if the cloud sync service is reachable and reports the pending change queue size.
- **printer / scanner / drawer:** Polls the status of configured peripherals.
- **backup:** Reports the timestamp and result of the last scheduled backup.

#### 18.3.2 Local Dashboard

The admin can access a “System Health” screen within the app. It presents the above information in a user‑friendly card layout with traffic‑light indicators (green for healthy, yellow for degraded, red for unhealthy). The screen also shows resource usage (CPU, memory) at a high level.

#### 18.3.3 Proactive Alerts

The system proactively displays non‑blocking toasts or banners when a degradation is detected:
- “Printer ‘Receipt Printer’ is offline. Sales can still be completed.”
- “Disk space is low (500 MB remaining). Please free up space to avoid issues.”
- “Cloud sync has been failing for 2 hours. Check your internet connection.”

These alerts appear in the admin’s view and are logged for support.

### 18.4 Backup Monitoring

Given the criticality of backups, the operational architecture includes explicit backup monitoring:

- **Backup Success/Failure Log:** Every backup attempt (manual or scheduled) writes a record to a `backup_log` table with timestamp, destination, size, status, and error message.
- **Backup Age Alert:** If no successful backup has been completed in the configured interval (e.g., 3 days), a warning is shown on the dashboard and, if configured, an in‑app notification is generated.
- **Restore Drill:** The admin can perform a “test restore” to a temporary location to verify backup integrity, without affecting the live database. This is an advanced feature suggested during onboarding and periodically reminded.

### 18.5 Performance Monitoring (Lightweight)

Full‑scale APM (Application Performance Monitoring) is not appropriate for a local desktop application. Instead, the system records lightweight performance counters:

- **Transaction Timers:** The service layer records the duration of key operations (sale save, FIFO deduction, journal posting, report generation). These are logged at DEBUG level and summarised as moving averages (e.g., “Average sale save time: 85 ms over last 50 sales”).
- **Database Query Slow Log:** Any database query exceeding a configurable threshold (default 500 ms) is logged at WARN level with the query text and parameters. This helps the development team identify missing indexes or inefficient queries in the field.
- **Memory & CPU:** The local server periodically logs its own memory usage and CPU load (at INFO level, every hour). This provides a baseline for capacity planning.

### 18.6 Cloud Service Operations (Amar Hisab Team)

The Cloud Sync Service follows standard cloud‑native operational practices. Key elements:

- **Infrastructure as Code:** All cloud resources (Kubernetes, PostgreSQL, Redis, object storage) are defined and provisioned using Terraform. This ensures reproducibility and disaster recovery of the cloud environment itself.
- **Metrics & Dashboards:** The Go services expose Prometheus metrics (request rate, latency, error rate, sync queue depth, active connections). Grafana dashboards provide real‑time visibility for the DevOps team.
- **Alerting:** Alertmanager rules notify the on‑call engineer of critical conditions: sync service pod crash looping, database connection pool exhaustion, high 5xx error rate, tenant‑reported conflict storms.
- **Log Aggregation:** Structured logs from all cloud services are shipped to a central log aggregator (e.g., Loki + Grafana, or Elastic Stack). They are indexed by `business_id` and `correlation_id` for efficient troubleshooting.
- **Database Maintenance:** Automated daily backups of the cloud PostgreSQL database with point‑in‑time recovery. Partition maintenance on the `cloud_change_log` table is scheduled during low‑traffic windows.
- **Canary Deployments:** New versions of the cloud service are deployed first to a small subset of tenants (canary) before full rollout, reducing the blast radius of potential regressions.

### 18.7 Remote Support & Diagnostics

The Amar Hisab support team needs the ability to assist users who encounter problems they cannot resolve themselves. The architecture provides a secure, consent‑based remote support mechanism.

#### 18.7.1 Support Ticket Generation
- From the Help screen, a user can “Generate Support Report”. This bundles:
  - The last 24 hours of log files (WARN and above, with sensitive data redacted).
  - The current health check report.
  - System information (OS version, app version, database size, hardware specs).
  - A user‑written description of the issue.
- The bundle is encrypted and saved locally. The user can then share it with support via email, Telegram, or a temporary upload link (if internet is available).

#### 18.7.2 Secure Remote Session (Future)
- For complex issues, a support engineer can initiate a remote support session request.
- The user receives an in‑app notification and must explicitly approve.
- Once approved, a secure, read‑only view of the application’s state (not full desktop control) is shared with the support engineer via a relay service. The engineer can view the database schema, logs, and configuration, but cannot execute write operations.
- The session is recorded (with user consent) for audit and training purposes.

### 18.8 Operational Runbooks (Summary)

The Operations Runbook (a separate document) contains step‑by‑step procedures for common operational tasks. Key runbooks include:

| Procedure | Description |
|-----------|-------------|
| **Starting the System** | Power on server, launch Amar Hisab, start local server, connect clients. |
| **Stopping the System** | Ensure all clients have saved work, stop local server, close application. |
| **Daily Backup** | Initiate manual backup to USB drive or cloud, verify success. |
| **Restore from Backup** | Stop server, replace database file with backup, restart, verify. |
| **Adding a New Client Device** | Install app on device, connect to Wi‑Fi, discover server, log in. |
| **Changing Business Type** | Run migration wizard, review changes, apply, verify data. |
| **Troubleshooting Printer Offline** | Check physical connections, restart printer, re‑pair Bluetooth, test print. |
| **Recovering from Database Corruption** | Shut down server, restore from latest backup, run integrity check, restart. |
| **Enabling Cloud Sync** | Create cloud account, link device, perform initial sync, verify. |

These runbooks are accessible directly from the Help menu and are written in plain language (Bengali and English) with screenshots.

### 18.9 Application Update Mechanism

The application must be kept up‑to‑date with minimal user effort.

- **Desktop:** On startup, the application checks for updates against a public update server (HTTPS). If a new version is available, it downloads the installer in the background. The user is prompted to install; the installer can perform an in‑place upgrade without losing data. Rollback is supported by keeping the previous version’s database backup.
- **Mobile:** Standard app store update mechanisms (Google Play, App Store) are used. The app has a minimum supported server version; if the server is too old, the client displays a message asking the admin to update the server.
- **Cloud Service:** Deployed via CI/CD pipeline. Database migrations are run automatically as part of deployment. Backward compatibility is maintained for at least one major version of the local sync client.

### 18.10 Operational Security

Operational procedures themselves must be secure:

- Backup files are encrypted before transport.
- Remote support sessions use end‑to‑end encryption and are ephemeral.
- Logs do not contain plain‑text secrets (passwords, API keys). A redaction filter is applied to structured log data.
- Access to the cloud operational dashboards and infrastructure is restricted to authorised DevOps personnel via strong authentication (SSO + MFA) and audit‑logged.

## 19. Development & Build Pipeline

The Amar Hisab engineering team must deliver a reliable, high‑quality product across six client platforms, three desktop server platforms, and a cloud service—all while maintaining a sustainable pace and ensuring that every commit is safe to release. It embodies the principles of **continuous integration, comprehensive automated testing, and deterministic, reproducible builds.**

```
└── README.md
```

The `app/` directory contains the Flutter project that targets mobile, desktop, and web. The `server/` directory is a separate Dart package for the local shelf server, which can be compiled into a standalone executable and bundled with the desktop app. The `cloud/` directory is the Go service. Shared proto definitions live in `proto/` and are used to generate code for both Dart and Go.

#### 19.1.2 Branching Strategy
The team uses **Trunk‑Based Development** with short‑lived feature branches.

- `main` is the trunk; it is always in a releasable state. Every commit to `main` triggers the full CI pipeline.
- Feature branches are created from `main` and merged via pull requests. They live for a maximum of a few days.
- Release branches (e.g., `release/1.4`) are created from `main` when a release is imminent. Only critical bug fixes are cherry‑picked into the release branch. The release branch is tagged (e.g., `v1.4.0`) when the build is finalised.
- Hotfix branches are created from `main` (or the release branch if critical), fixed, and merged back into both `main` and the release branch.

This strategy encourages small, incremental changes that are continuously integrated, reducing merge conflicts and ensuring that the pipeline feedback loop is short.

### 19.2 Continuous Integration Pipeline

Every push to `main` and every pull request triggers the CI pipeline, defined in GitHub Actions (or an equivalent CI platform). The pipeline is designed to provide rapid feedback—developers should know within 10–15 minutes whether their change is safe.

#### 19.2.1 Pipeline Stages

1. **Static Analysis & Linting**
   - **Dart:** `dart format --set-exit-if-changed` (code formatting), `flutter analyze` (static analysis with strict mode), `dart pub publish --dry-run` (dependency integrity).
   - **Go:** `go vet`, `staticcheck`, `golangci-lint`.
   - **Proto:** `buf lint` and `buf breaking` (ensuring backward compatibility of sync API).
   - This stage catches style violations, potential null‑safety issues, unused imports, and breaking changes before a single test is run.

2. **Code Generation & Build Verification**
   - Run code generators: `build_runner` for Dart (JSON serialization, freezed models), `protoc` for Dart and Go stubs.
   - Verify that generated code is up‑to‑date (CI fails if generated files are not committed).
   - Build the Flutter app and the Dart server for the primary target (Linux, as the CI runner is Linux) to ensure compilation succeeds. This catches syntax errors and missing imports that static analysis might miss.

3. **Unit & Widget Testing**
   - **Dart:** Execute all `flutter test` (unit and widget tests) and `dart test` (pure Dart tests) across the app and server packages.
   - **Go:** Execute `go test ./...` for the cloud service.
   - Unit tests run in milliseconds; widget tests render Flutter widgets in a headless environment. The entire test suite should complete in under 5 minutes.
   - Coverage reports are generated and uploaded. A coverage threshold (e.g., 70% for domain and application layers) is enforced; the CI fails if coverage drops below the threshold on new code.

4. **Integration Testing**
   - Spin up a local SQLite database (using `sqflite_common_ffi` for desktop‑like testing) and run integration tests that validate the service layer against a real database.
   - For Go, spin up a test PostgreSQL instance using a container, run migration, and execute integration tests.
   - These tests are fewer than unit tests but cover critical paths (FIFO deduction, accounting posting, sync push/pull).

5. **End‑to‑End Testing (Nightly)**
   - Full end‑to‑end tests that start the local server, connect a simulated Flutter client, and perform complete workflows (sale, purchase, sync) are too slow for per‑commit CI. They are executed nightly (or on demand) against the `main` branch.
   - A separate pipeline deploys a canary cloud sync service and runs end‑to‑end multi‑device sync scenarios. Failures are reported to the team’s alert channel.

6. **Build & Artifact Publication (on tag)**
   - When a Git tag matching `v*` is pushed, the pipeline builds the final release artifacts for all platforms.
   - This stage is described in detail in Section 19.5.

#### 19.2.2 CI Notifications & Badges
- Build status is prominently displayed on the repository’s README (badge).
- Failures are immediately notified to the team’s communication channel (Slack/Teams).
- A “flaky test” quarantine process exists: if a test fails intermittently, it is quarantined (moved to a separate suite) and fixed with high priority, ensuring that the main CI signal remains trustworthy.

### 19.3 Testing Strategy & Quality Gates

The testing pyramid guides the distribution of test effort.

#### 19.3.1 Unit Tests (Base of Pyramid)
- **Scope:** Pure business logic (domain entities, value objects, domain services like `DiscountCalculator`, `FIFOEngine`).
- **Characteristics:** Fast (< 100ms per test), no I/O, no database. Dependencies are mocked or stubbed.
- **Goal:** 80%+ coverage of the `domain/` layer. Every business rule (e.g., “discount cannot exceed 100%”, “FIFO always picks earliest expiry”) is encoded as a unit test.

#### 19.3.2 Widget Tests (Middle)
- **Scope:** Individual Flutter widgets and UI components in isolation.
- **Characteristics:** Rendered in a headless Flutter environment. Interactions (tap, scroll) are simulated.
- **Goal:** Ensure UI components correctly display data and respond to user input. Not every pixel is tested, but critical components (POS cart, payment dialog, ledger view) are covered.

#### 19.3.3 Integration Tests (Upper Middle)
- **Scope:** Service layer + real SQLite database. Tests exercise the `application/` services with actual database transactions.
- **Example:** Create a product, create a purchase (which triggers inventory update), then create a sale (which triggers FIFO deduction), and verify final stock quantities and COGS.
- **Characteristics:** Use `sqflite_common_ffi` to run SQLite natively on the CI server (no Android emulator needed). Each test runs in a fresh, temporary database.

#### 19.3.4 End‑to‑End Tests (Tip)
- **Scope:** Full system tests: Flutter client → local server → SQLite → (optional) cloud sync.
- **Characteristics:** Run on actual devices or emulators. These are the most expensive to execute and maintain; hence, they are run nightly and are limited to smoke‑test critical user journeys:
  1. POS sale with cash payment.
  2. Purchase with batch tracking.
  3. Student enrollment, fee payment, QR‑based self‑service inquiry.
  4. Cloud sync between two simulated devices.

#### 19.3.5 Manual Testing & Exploratory
- Before a release, a manual smoke test is performed on physical hardware (Android tablet, Windows desktop, thermal printer). The QA checklist covers the specific features changed in that release.
- Exploratory testing sessions are conducted by the team to discover edge cases that automated tests miss.

### 19.4 Code Quality & Review

Every pull request must be approved by at least one other engineer before merging. The review checklist includes:

- Adherence to the module structure and layered architecture.
- Presence of unit tests for new business logic.
- Error handling: all expected failure modes return appropriate API errors.
- Database migrations are non‑destructive and backward‑compatible.
- Proto changes do not break backward compatibility (or are clearly versioned).

Automated checks enforce code style, but architectural conformance is currently a human responsibility, guided by this Architecture Book.

### 19.5 Build & Release Process

#### 19.5.1 Desktop Application (Local Server + Client)
The desktop application is the primary distribution for local servers. It includes both the local server and the full Flutter UI (it can act as client and server).

- **Build Platform:** GitHub Actions runners (Linux, macOS, Windows). Flutter’s desktop support requires platform‑specific runners for compilation.
- **Artifacts:**
  - **Windows:** `.exe` installer (created with `msix` or `inno_setup`). Code‑signed with an EV certificate.
  - **macOS:** `.app` bundle inside a `.dmg`. Notarized by Apple.
  - **Linux:** `.deb` and `.AppImage`.
- **Versioning:** The version is defined in `pubspec.yaml` and the tag. The CI injects the build number (e.g., `1.4.0+42`) and the Git hash into the application.
- **Auto‑Update:** The desktop app includes an update client that checks a public update server (hosted on Cloud Storage) for the latest version at startup. If a new version is available, the user is prompted to download and install. The update is differential (binary patch) when possible, otherwise full installer.

#### 19.5.2 Mobile Applications (Client)
- **Android:** Built with Flutter, artifact is `.aab` (Android App Bundle) for Google Play, or `.apk` for direct distribution. Published to Google Play Console via CI.
- **iOS:** Built on macOS runner, artifact is `.ipa`. Published to App Store Connect via CI (using `fastlane`).
- Both apps share the same Dart codebase as the desktop client. The mobile client does not include the local server capabilities by default; it connects to a desktop server. However, the “Standalone Mobile” mode is a build variant that includes the server library.

#### 19.5.3 Cloud Service
- **Container:** The Go service is compiled into a statically linked binary and packaged into a minimal Docker image (scratch or alpine).
- **Registry:** The image is pushed to a container registry (Docker Hub, GHCR, or AWS ECR) with tags corresponding to the Git tag and `latest`.
- **Deployment:** Kubernetes manifests (or Helm charts) are stored in the `cloud/` directory. The CI/CD pipeline can optionally deploy to a staging environment on tag creation. Production deployment is triggered manually (or via progressive delivery) by the DevOps engineer.

#### 19.5.4 Release Cadence
- The team aims for a **monthly minor release** (e.g., 1.4.0, 1.5.0), synchronising across all platforms.
- **Patch releases** (1.4.1) for critical bug fixes are released as needed.
- Release notes are auto‑generated from conventional commit messages and curated with user‑facing summaries.

### 19.6 Environment Management

- **Development:** Engineers run the Flutter app on their own machines, connecting to a locally running server (or the built‑in server). SQLite is used. No cloud dependencies are required.
- **Staging:** A cloud staging environment mirrors production. The sync service is deployed here. Selected test businesses can opt in to test pre‑release versions of the mobile app via TestFlight / Google Play Beta.
- **Production:** The live cloud sync service. Desktop and mobile apps are distributed through official channels. The local server is always “production” from the user’s perspective; there is no staging mode for local databases—the safety net is the backup system.

### 19.7 Dependency Management & Supply Chain Security

- **Dart:** Dependencies are pinned in `pubspec.lock`. The CI pipeline runs `dart pub outdated` and reports on outdated packages. A scheduled job audits dependencies for known vulnerabilities (using `dart pub audit` or OSS‑Fuzz integration when available).
- **Go:** Dependencies are pinned in `go.sum`. `govulncheck` is run in CI.
- **SBOM:** A Software Bill of Materials (in SPDX or CycloneDX format) is generated during the release build and archived.
- All third‑party code is reviewed for licenses (must be compatible with MIT or Apache 2.0). A license checker runs in CI to prevent the introduction of restrictive licenses.

The Development & Build Pipeline ensures that Amar Hisab can be developed with confidence, released with quality, and maintained efficiently by a team that values both speed and stability. The heavy investment in automation—from formatting checks to multi‑platform build artifacts—pays for itself many times over by preventing regressions and reducing the manual effort required for each release.

### Appendix A: Glossary

| Term | Definition |
|------|------------|
| **Aggregate** | A cluster of domain objects that are treated as a single unit for data changes (e.g., a `Sale` and its `SaleItems`). |
| **Bounded Context** | A logical boundary within which a particular domain model is defined and applicable (e.g., Sales, Inventory, Accounting). |
| **Business Type** | A named configuration profile (e.g., Pharmacy, Grocery, Academy) that determines the active modules, chart of accounts, and UI layout. |
| **Change Log** | A local database table (`change_log`) that records every data mutation as an event for synchronisation. |
| **Chart of Accounts (CoA)** | A structured list of all financial accounts used by the double‑entry accounting system. |
| **Cloud Sync Service** | The optional, cloud‑hosted service that relays and merges change events between devices for multi‑device and multi‑branch synchronisation. |
| **Correlation ID** | A unique identifier attached to a request or background job, used to trace related log entries across different modules. |
| **Domain Event** | An in‑process message representing a significant business occurrence (e.g., `SaleCompleted`), used to decouple modules. |
| **Double‑Entry Accounting** | A system where every financial transaction has equal and opposite effects in at least two different accounts (debits = credits). |
| **Event Sourcing** | A pattern where state changes are stored as a sequence of immutable events (e.g., `StockMovement`) rather than just the current state. |
| **FIFO (First‑In, First‑Out)** | An inventory valuation method where the oldest batch of a product is assumed to be sold first. |
| **Idempotency** | The property of an operation where multiple identical requests have the same effect as a single request (used for safe sync retries). |
| **JWT (JSON Web Token)** | A compact, URL‑safe token used for authentication and authorisation, containing claims about the user. |
| **Local Server** | The Amar Hisab desktop application running as an HTTP server on the local network, managing the business database and logic. |
| **mDNS (Multicast DNS)** | A protocol that allows devices on a local network to discover each other by hostname (e.g., `amarhisab.local`) without a central DNS server. |
| **Module** | A self‑contained unit of software that encapsulates a specific business capability (e.g., Sales Module). |
| **Offline‑First** | An architectural approach where the application functions fully without an internet connection, syncing data when connectivity is available. |
| **Plugin** | An implementation of a defined interface that integrates an external service or hardware (e.g., a specific payment gateway). |
| **Posting Template** | A predefined set of accounting rules that maps a business event (e.g., a cash sale) to the appropriate double‑entry journal lines. |
| **Public Portal** | The lightweight web application served by the local server, allowing students or customers to view their own data via QR code without an app. |
| **RBAC (Role‑Based Access Control)** | A method of restricting system access based on the roles of individual users (Owner, Manager, Cashier, etc.). |
| **Repository** | An abstraction layer that mediates between the domain model and the database, providing collection‑like access to aggregates. |
| **Shelf** | A Dart web server framework used to build the local HTTP API. |
| **SQLite** | The embedded, file‑based relational database used for all local data storage. |
| **Sync Engine** | The component within the local server that pushes local changes to the cloud and pulls remote changes. |
| **Transactional Outbox** | A pattern where messages (or events) are stored in the same database transaction as the business data, guaranteeing they are not lost. |
| **Tombstone** | A marker record used in distributed systems to indicate that an entity has been deleted, preventing its resurrection during sync. |
| **Value Object** | An immutable object that represents a descriptive aspect of the domain with no conceptual identity (e.g., `Money`, `InvoiceNumber`). |

| **ADR‑004** | 2025‑11‑15 | Use **Event Sourcing for Inventory** | Stock levels must be auditable and easily synced across devices. Immutable stock movement events provide a complete history and simplify sync merging. | Increased storage for stock movements; stock queries require aggregation or a materialised summary table. | **ADR‑005** | 2025‑11‑20 | Implement **Business Type Configuration** via declarative manifests | The system must support many verticals without forking. Some dynamic UI overhead is accepted. |
| **ADR‑006** | 2025‑12‑01 | Use **Double‑Entry Accounting** with auto‑posting templates | Accurate financial reporting is mandatory. Manual journal entry is error‑prone for small business owners. Pre‑defined posting templates map each business event to the correct double‑entry, ensuring consistency. | The template engine adds initial complexity but enables business‑type‑specific accounting without code changes. |
| **ADR‑007** | 2025‑12‑10 | Separate **Domain Events** (in‑process) from **Sync Events** (change log) | Domain events decouple modules within the server; sync events are the durable source for distributed state. A bridge translates domain events into sync entries, but the transactional outbox guarantees sync entries are always written with the business data. | Two event channels exist, which could cause confusion. Clear documentation and naming conventions mitigate this. |
| **ADR‑008** | 2025‑12‑15 | Use **Go** for the Cloud Sync Service | The cloud service needs to handle high concurrency and be resource‑efficient. Go’s goroutines and compiled binaries suit this well. | Introduces a second language to the stack. The scope is limited to the sync service, and strong gRPC contracts keep integration straightforward. |
| **ADR‑009** | 2026‑01‑10 | Default to **HTTP on LAN** for local API (optional TLS) | Requiring TLS certificate management from non‑technical users would be a major adoption barrier. The local network is assumed to be secured by Wi‑Fi encryption. An optional certificate pinning mode is available for security‑conscious users. | Traffic is not encrypted by default within the LAN; risk is accepted given the target environment. |
| **ADR‑010** | 2026‑02‑01 | Adopt **Trunk‑Based Development** with short‑lived feature branches | The team is small; long‑lived branches lead to merge hell. Trunk‑based development encourages small, incremental commits that are continuously integrated. | Requires discipline in feature flagging and test coverage. Hotfix process must be efficient. |
| **ADR‑011** | 2026‑02‑15 | Use **Code Generation** for models, JSON, and repositories | Boilerplate code for Dart data classes, serialization, and SQL queries is error‑prone. Code generation (`freezed`, `json_serializable`, custom generators) reduces errors and improves developer velocity. | Build process includes code generation step. Developers must understand the generated code’s behaviour. |
| **ADR‑012** | 2026‑03‑01 | Deploy Cloud Sync Service on **Kubernetes** | Provides horizontal scaling, self‑healing, and declarative configuration. The cloud team is proficient with Kubernetes. | Adds infrastructure complexity for the cloud service only; local server remains simple. |
