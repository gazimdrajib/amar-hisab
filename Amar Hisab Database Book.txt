## 1. Introduction

This book is the definitive reference for the physical database schema of **Amar Hisab**. It documents every table, column, data type, constraint, index, and relationship in the system. The schema is designed to support the offline‑first, multi‑business‑type architecture while maintaining strong data integrity, enabling efficient synchronisation, and providing a complete audit trail.

### 1.1 Scope
- Complete DDL for all tables in the local SQLite database.
- Column descriptions and business rules.
- Primary keys, foreign keys, unique constraints, and check constraints.
- Recommended indexes for performance.
- Views and materialised summary tables (where applicable).
- Data lifecycle policies (archival, retention).
- Migration strategy and versioning.

### 1.2 Database Engine
- **Local:** SQLite 3.x (required). The database file uses WAL journal mode, full‑text search (FTS5) for product/customer search, and optional encryption via SQLCipher.
- **Cloud (optional):** PostgreSQL 15+ for the Sync Service. The cloud schema is a superset; only the local schema is documented here. The cloud tables for sync (`cloud_change_log`, etc.) are defined in the Sync Service repository.

### 1.3 Naming Conventions
- Tables are named in lower‑case `snake_case`, pluralised for collections (e.g., `sales`, `products`).
- Primary keys are always `id INTEGER PRIMARY KEY AUTOINCREMENT`.
- Foreign keys follow the pattern `{referenced_table}_id` (e.g., `customer_id`).
- Timestamps are stored as ISO‑8601 text (`YYYY-MM-DD HH:MM:SS` or `YYYY-MM-DD` for dates). Use `TEXT` type.
- Monetary values are stored as `REAL` (SQLite does not have a decimal type; application ensures proper rounding).
- Soft‑delete columns use `is_deleted INTEGER DEFAULT 0` and `deleted_at TEXT`.

## 2. Entity‑Relationship Overview

The schema is organised into the following modules:
- **Core:** businesses, warehouses, users, roles, permissions, settings.
- **Product & Inventory:** products, categories, units, batches, stock, stock_movements.
- **Sales:** sales, sale_items, sale_payments, sale_item_batches, sales_returns, quotations, delivery_notes.
- **Purchase:** purchases, purchase_items, purchase_orders, purchase_returns, supplier_payments.
- **Accounting:** chart_of_accounts, journal_entries, journal_lines, posting_templates.
- **Customer & Supplier:** customers, customer_groups, suppliers, customer_tokens.
- **Education:** academic_batches, student_enrollments, student_attendances, exam_results, student_secrets.
- **HRM:** employees, attendance, salary.
- **Security & Audit:** users, roles, permissions, audit_log.
- **Sync & Change Log:** change_log, sync_state, device_registry.

Relationships are enforced via foreign keys in SQLite only when `PRAGMA foreign_keys = ON` (enabled by the application).

In addition to the indexes listed per table, the following composite indexes are critical:

- `sales(business_id, sale_date DESC)`
- `sale_items(sale_id)`
- `sale_payments(sale_id)`
- `purchases(business_id, purchase_date DESC)`
- `purchase_items(purchase_id)`
- `stock(product_id, warehouse_id, batch_id)`
- `stock_movements(product_id, date)`
- `batches(product_id, expiry_date)`
- `journal_lines(journal_entry_id)`
- `journal_lines(account_id, journal_entry_id)` (for ledger queries)
- `audit_log(entity_type, entity_id)`
- `change_log(device_id, sync_status)`

Full‑Text Search (FTS5) virtual tables are created for `products(name, code, barcode)` and `customers(name, phone)`. These are kept in sync via triggers or application logic.

## 5. Views (Optional)

Pre‑defined views for common reports (not stored as separate objects but documented here for consistency):

- `customer_ledger_view`: UNION of sales and payments for a customer.
- `supplier_ledger_view`: UNION of purchases and payments for a supplier.
- `trial_balance_view`: Aggregated debits and credits per account up to a date.
- `stock_valuation_view`: `batches.current_quantity * cost_price` grouped by product/warehouse.

These can be implemented as in‑app queries rather than database views to keep the schema simple.

## 6. Data Archival and Retention

- **Active Data:** Current and previous fiscal year remain in the main database.
- **Warm Archive:** At the start of a new fiscal year, an archival job moves closed sales, purchases, and journal entries older than (current year – 2) into an `archive_YYYY.db` SQLite file. The main database retains summary records (`daily_sales_summary`, etc.).
- **Audit Log:** Retained for 2 years in the main database, then exported to encrypted CSV and deleted.
- **Change Log:** After successful sync, entries older than 30 days are purged (configurable). The cloud retains the event log as long as the tenant is active.
- **Student data:** Attendance and exam results are kept indefinitely for the lifetime of the academy business, but can be anonymised upon student request.

All archival operations are manual (triggered by admin) but scripted in the application. The DB schema includes `is_archived` flags where appropriate.

---

## 7. Migration Strategy

- The database includes a `schema_version` table with a single row storing the current version number.
- On application startup, the version is compared with the required version. If lower, a migration runner executes sequentially numbered SQL scripts (e.g., `migration_1_to_2.sql`).
- Migrations are additive (`ALTER TABLE ADD COLUMN`), never destructive. Dropping columns or tables requires a major version and explicit user consent (with backup).
- The cloud PostgreSQL schema is managed by `golang-migrate` and kept backward‑compatible.
