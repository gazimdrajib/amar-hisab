# Amar Hisab Proto Contract Book  
**Document Version:** 1.0  
**Last Updated:** 2026-07-15  
**Audience:** API Consumers (Frontend Developers, Third‑Party Integrators), Backend Developers, QA Engineers

## 1. Introduction

The Proto Contract Book defines every external interface of the Amar Hisab system. It is the single source of truth for:

- **REST API** – consumed by the Flutter clients, the Public Portal, and potentially third‑party integrations.  
- **gRPC Sync Service** – used between the Local Server and the optional Cloud Sync Service.  
- **Public Portal Endpoints** – accessed by students, parents, and customers via QR codes.  

All contracts are versioned and governed by strict backward‑compatibility rules. The book is intended to be used alongside the Architecture Book and Database Book.

### 1.1 Document Structure
- **Section 2** – REST API conventions (status codes, pagination, authentication).  
- **Section 3** – REST API endpoint reference, organised by module.  
- **Section 4** – gRPC sync service contracts (.proto definitions).  
- **Section 5** – Shared data types and enums.  
- **Section 6** – Versioning and deprecation policy.

## 2. REST API Conventions

All REST endpoints share a common set of behaviours.

### 2.1 Base URL
- **Local Network:** `http://{server-ip}:8080` or `http://amarhisab.local:8080`
- **Cloud (future public API):** `https://api.amarhisab.com`

### 2.2 Content Type
- `application/json` for both request and response bodies.

### 2.3 Authentication
- **Internal API:**  
  Header `Authorization: Bearer <JWT>` required for all endpoints except `/auth/login`.  
  The JWT must be obtained from `/api/v1/auth/login` and contains `user_id`, `role`, `business_id`.
- **Public Portal API:**  
  No global auth; uses portal tokens (embedded in QR URL) or student ID + secret for login.

### 2.4 HTTP Methods
- `GET` – Retrieve resource(s)  
- `POST` – Create a new resource  
- `PUT` – Full update (idempotent)  
- `PATCH` – Partial update  
- `DELETE` – Soft‑delete / deactivate

### 2.5 Status Codes
| Code | Meaning |
|------|---------|
| 200 OK | Request succeeded (GET, PUT, PATCH) |
| 201 Created | Resource created; `Location` header points to new resource |
| 204 No Content | Successful DELETE or operation with no body |
| 400 Bad Request | Invalid input; see `error` object |
| 401 Unauthorized | Missing or invalid token |
| 403 Forbidden | Insufficient permissions |
| 404 Not Found | Resource does not exist |
| 409 Conflict | Business rule violation (e.g., duplicate invoice) |
| 422 Unprocessable Entity | Semantic validation error (e.g., unbalanced journal) |
| 429 Too Many Requests | Rate limiting |
| 500 Internal Server Error | Unexpected server failure |

### 2.6 Response Envelope
Every JSON response follows this structure:

**Success:**
```json
{
  "success": true,
  "data": { ... },
  "meta": { ... }        // optional, for pagination
}
```

**Error:**
```json
{
  "success": false,
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "Insufficient stock for product Napa Extra.",
    "details": { ... }
  }
}
```

### 2.7 Pagination
Collection endpoints support cursor‑based pagination via query parameters:
- `limit` (default 20, max 100)
- `cursor` (opaque string from previous `meta.next_cursor`)

The `meta` object in the response:
```json
{
  "next_cursor": "eyJpZCI6MTIzfQ==",
  "has_more": true,
  "total_count": 250
}
```
If `has_more` is `false`, all items have been fetched.

### 2.8 Filtering & Sorting
Standard query parameters for collections:
- `?status=Completed,Draft` – filter by field (comma‑separated)
- `?from_date=2026-07-01&to_date=2026-07-15` – date range
- `?customer_id=42` – foreign key filter
- `?sort=-created_at` – sort by field; `-` indicates descending

### 2.9 API Versioning
The API version is embedded in the URL path: `/api/v1/`, `/api/v2/`.  
The version number changes only on backwards‑incompatible modifications. Additions (new endpoints, new optional fields) do **not** change the version. The server may support multiple versions simultaneously during a deprecation window.

## 4. gRPC Sync Service Contracts

The sync service uses **gRPC** with Protocol Buffers. The `.proto` file is the source of truth, stored at `proto/sync/v1/sync.proto`.

### 4.1 Service Definition

```protobuf
syntax = "proto3";
package amarhisab.sync.v1;

service SyncService {
  // Push local changes to the cloud.
  rpc PushBatch(PushBatchRequest) returns (PushBatchResponse);

  // Pull remote changes since the last known sequence.
  rpc PullChanges(PullRequest) returns (stream ChangeEvent);

  // (Future) Bidirectional real‑time sync stream.
  rpc SyncStream(stream ChangeEvent) returns (stream ChangeEvent);
}

message PushBatchRequest {
  string device_id = 1;
  int64 last_synced_sequence = 2;
  repeated ChangeEvent changes = 3;
}

message PushBatchResponse {
  bool success = 1;
  int64 accepted_sequence = 2;
  repeated Conflict conflicts = 3;
}

message Conflict {
  string change_id = 1;
  string reason = 2;
  bytes local_version = 3;
  bytes remote_version = 4;
}

message PullRequest {
  string device_id = 1;
  int64 last_remote_sequence = 2;
  string business_id = 3;
}

message ChangeEvent {
  string change_id = 1;       // UUID
  string entity_type = 2;
  int64 entity_id = 3;
  string operation = 4;       // "INSERT", "UPDATE", "DELETE"
  bytes payload = 5;          // JSON
  bytes old_values = 6;       // JSON
  int64 timestamp_ms = 7;
  int64 sequence = 8;         // device‑local sequence
  string device_id = 9;
}
```

**Service Details:**
- **PushBatch:** The local server sends an ordered batch of changes. The cloud processes them in order, applies conflict resolution (last‑write‑wins by default), and returns the highest accepted sequence number.
- **PullChanges:** Server‑side streaming call. The cloud streams all events with a global sequence greater than `last_remote_sequence`. The client applies them in order.
- **SyncStream:** Bidirectional stream for near‑real‑time sync (future). Both sides can send and receive changes simultaneously.

**Idempotency:**  
The cloud deduplicates by `change_id`. Duplicate pushes are acknowledged but produce no side effects.

**Authentication:**  
gRPC channels are secured with mTLS using device certificates, or a device‑specific JWT in the metadata.

### 4.2 Proto Versioning
- Package name includes major version (`amarhisab.sync.v1`).  
- New fields may be added with new tag numbers; old fields must not be removed or renumbered.  
- If a breaking change is required, a new service version (e.g., `SyncServiceV2`) is introduced and both coexist during migration.

## 5. Shared Data Types & Enums

### 5.1 Common Fields
- `business_id` (integer) – mandatory for multi‑tenant isolation.  
- `created_at`, `updated_at` (ISO‑8601 string) – timestamps.  
- `created_by` (integer) – user ID who performed the action.  
- `status` – many entities have a status field; possible values are defined per entity.

### 5.2 Money
All monetary values are represented as `REAL` (double) in JSON and handled with proper rounding in the application. The currency is always the one configured for the business (default BDT). Currently, no multi‑currency amounts are exposed in a single object; if needed, a `{ amount: 100.0, currency: "BDT" }` structure will be introduced in a future version.

### 5.3 Common Enums
- **SaleType:** `POS`, `Retail`, `Wholesale`, `Quotation`, `Delivery`
- **PaymentMethod:** `Cash`, `Bank`, `bKash`, `Nagad`, `Card`, `Wallet`
- **PurchaseStatus:** `Draft`, `Sent`, `Received`, `Cancelled`
- **InvoiceStatus:** `Draft`, `Hold`, `Completed`, `Returned`, `Cancelled`
- **MovementType:** `Purchase`, `Sale`, `Transfer_In`, `Transfer_Out`, `Adjustment`, `Damage`, `Return`, `Expiry`
- **AccountType:** `Asset`, `Liability`, `Equity`, `Revenue`, `Expense`, `Contra Revenue`

These are transmitted as strings and validated by the server.

## 6. Versioning & Deprecation Policy

### 6.1 REST API Versions
- The current version is `v1`.  
- When a breaking change is necessary (e.g., removing a field, changing a field type), a new version (`v2`) is introduced.  
- The old version is maintained for **6 months** after the new version’s release, during which time a deprecation notice is added to the response header (`Sunset: Sat, 01 Jan 2027 00:00:00 GMT`) and documented.  
- Clients are encouraged to migrate during the deprecation window.

### 6.2 Non‑Breaking Changes
The following are considered backward‑compatible and do **not** require a version bump:
- Adding a new endpoint.
- Adding a new optional request field.
- Adding a new field to a response (clients must be tolerant of unknown fields).
- Expanding an enum with a new value (clients must treat unrecognised values gracefully).

### 6.3 gRPC Versions
- Services follow the same major‑version principle as the REST API.  
- Breaking changes result in a new service (`SyncServiceV2`) that coexists with the old version.  
- Field additions are safe; field removals or type changes are breaking.  
- Migration strategy: New clients use the new service; old clients continue to use the old service until all clients are updated.
